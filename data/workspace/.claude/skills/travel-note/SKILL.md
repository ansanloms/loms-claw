# 旅行ノートの書き方

`memory/travel/` 配下で旅行 1 件につき 1 つの Markdown ノートを管理する手順。

## 位置付け

**このノートはユーザは閲覧しない (ユーザの環境からアクセス手段が無い)。** お前自身が次回以降の計画時に過去の旅行傾向 (行き先・装備・ペース・好みの宿レベル等) を参照するための AI 専用メモとして運用しろ。ユーザに伝えたい情報は Discord チャンネル/スレッドで完結させる (「ノートに書いた」と報告する必要はない)。スケジュールを常時見える形で出す手段はノートではなく Discord のピン投稿 (「Discord ピン投稿」節)。

旅行終了後もファイルは削除するな。事後振り返りを埋めて、次回計画の材料にする。

## Discord 返信との関係

ノートの更新と Discord の返信は別の成果物で、ノートを更新したことは返信を省く理由にならない。

- ノートに書く情報のうちユーザに関わるもの (決めたカットオフライン・撤退条件、仕込んだ一時 cron の発火時刻と確認対象、日程・status の変更、振り返りの結論と申し送り) は、返信の本文にそのまま書く。ノートのファイル名や見出しを示して参照させない。
- 「ノートに書いた」「ノートを更新した」「詳細はノートを参照」で返信を終えない。ノートを更新した事実そのものは報告不要で、報告するのは中身。
- 返信に載せる量を絞るときは要点を選ぶ。省いた分をノートで補うという構成にしない。理由: ユーザはノートを読めないため補いにならない。

なお、まだ具体化していない行き先の種や、個別の旅行に紐付かない定番情報は `memory/travel/PLANS.md` が持つ。具体的な計画・相談が始まった時点でこの skill の手順でノート化する。`PLANS.md` が存在しない場合は「種がまだ 1 件も無い」状態であり異常ではない。新たに種を書く際に存在しなければ次の見出しだけの雛形で作成する。

```markdown
# 行きたい場所の種

# よく使う旅行情報
```

## ファイル命名

- パスは `memory/travel/YYYYMMDD-<旅行概要>.md`。`YYYYMMDD` は出発日、`<旅行概要>` は行き先のスラッグ (英小文字、ハイフン区切り)。
  - 例: `memory/travel/20260501-shizuoka.md`、`memory/travel/20260608-takao.md`、`memory/travel/20260720-yakushima-trek.md`
- スラッグは行き先の地名のローマ字を基本とする。
  - 日本語名に地形語 (〜半島・〜湖・〜山等) が含まれるならローマ字のまま含める (英訳しない)。例: `izu-oshima`、`sagamiko`。
  - 同じ行き先の別計画と区別する必要があるときだけルート名等の修飾を足す (例: `tonotake-omoteone`)。
- 出発日が未定の段階では `memory/travel/TBD-<旅行概要>.md` とし、日程確定時に `YYYYMMDD-` へリネームする。延期等で日程が未定に戻ったら `TBD-` へ戻す。
- Discord スレッド名とファイル名は同じ旅行を指すよう揃える (例: `2026年5月1-3日 静岡` と `20260501-shizuoka.md`)。スレッド名の変更は discord skill で行う。Discord を操作できない文脈ではファイル側だけ更新し、スレッド名は次に Discord を操作できるときに追従させる。

## Discord スレッドの設定

旅行用のスレッドを立てたら、**そのスレッドに `active: true` を設定しろ。** 旅行の相談はスレッド内で往復するため、毎回メンションさせるのは煩わしい。

```bash
curl -s -X PATCH -H 'Content-Type: application/json' \
  -d '{"active":true}' \
  http://127.0.0.1:3000/settings/<スレッド ID>
```

`{id}` にスレッド ID をそのまま渡せばよい。書き込み先はスレッドのスコープだけで、親チャンネルの設定は変わらない。手順の詳細は `settings` skill (`.claude/skills/settings/SKILL.md`) を参照しろ。

- スレッド作成と同じ流れで設定する。作成だけして設定を忘れると、そのスレッドはメンション必須のまま残る。
- 既存の旅行スレッドで設定が漏れていることに気付いたら、その場で同じ PATCH を叩いて補え。
- 旅行が終わってスレッドを使わなくなっても、`active` を戻す必要はない。アーカイブされたスレッドには投稿が来ない。

## 新規作成

この skill の `assets/NOTE.md` を起点にコピーして使う。相対パスはすべてワークスペースルート (cwd) を起点とする。`memory/travel/` は `.gitignore` で除外されており初期状態では存在しないため、`mkdir -p` で作成してからコピーする。

```sh
mkdir -p memory/travel
cp .claude/skills/travel-note/assets/NOTE.md memory/travel/YYYYMMDD-<旅行概要>.md
```

cp は手段の一例。テンプレートの本文構造 (`##` 見出し: 計画/装備/予約・チケット/緊急連絡/当日メモ/事後振り返り。各見出し配下の `###` 見出しを含めた全体を指す) と frontmatter のキー構成を保って新規作成できれば、ファイルツールで直接書いても構わない。テンプレートには説明を書いていない。各欄の目的と埋め方は「本文の欄」節、キーの意味は「frontmatter の運用」節が持つ。cp せず直接書く場合でも「撤退基準」「一時 cron 記録」の 2 節は省略しないこと。理由: 運用上の意味を持つ (「本文の欄」節)。

- 「参照した知見」を埋める。出典は 2 系統。
  - `memory/travel/PLANS.md` の「よく使う旅行情報」のうち、`tags` と行き先に該当する小見出し。
  - `tags` または `destination` が重なる過去ノートの「事後振り返り」(実績ペース・装備の過不足・次回への申し送り)。絞り込みは「過去ノートの参照」節の手順で行う。
  - 適用した項目だけを出典付きで書き、PLANS.md を丸写ししない。小見出しが該当しても、要素ごとにこの旅行の前提 (日帰りか宿泊か・移動手段・時間帯等) に合うものだけを書く。適用するものが無ければ「該当なし」と書く (空欄 = 未参照)。
  - 出典どうしが矛盾する場合は、新しい過去ノートの申し送りを PLANS.md の一般則より優先し、矛盾した旨を「参照した知見」に書く。理由: travel-digest が PLANS.md 側を直す材料にする。
- frontmatter を埋める (次節)。
- 形態に該当しない装備サブセクションは削れ。
- 削るのは `<...>` で囲まれた値プレースホルダだけ (実値に置き換えるか、書けなければ行ごと削る)。見出しと、値が空のラベル行 (「- 交通:」等) は構造なので残し、後で埋める。
- 事前計画段階では空欄でも構わない。旅行進行とともに埋めていけ。
- `memory/travel/PLANS.md` の「行きたい場所の種」から昇格した場合は、該当の行を PLANS.md から消す。
- `assets/` 配下のテンプレート自体はこの skill では編集しない (テンプレートの改訂は skill 外の運用として行う)。改訂があっても既存ノートへは遡及適用しない (既存ノートの見出し・欄はそのまま使う。旧テンプレート由来の括弧書きが見出しや欄に残っていてもそのままでよい)。

## 本文の欄

`assets/NOTE.md` の各欄の目的と埋め方。テンプレート側には説明を書かないので、ここが正本。

- **計画** の見出し直下: 同行者がいる場合に人数・関係まで書く。単独なら何も書かない。
- **参照した知見**: `PLANS.md` の「よく使う旅行情報」と、tags・行き先が近い過去ノートの事後振り返りから、この旅行に適用した項目を出典付きで書く (選び方は「新規作成」節)。出典は PLANS.md の小見出し名、または過去ノートのファイル名。1 要素 1 行にし、出典が同じでも要素が違えば行を分ける。理由: 事後振り返りで要素ごとに当否を検証するため。適用するものが無ければ「該当なし」と書く。理由: 空欄 = 未参照、と区別するため。
- **移動 / 宿泊**: 区間・手段・時刻・予約番号、日付・宿泊先・価格帯・予約状況。ピン投稿のために引いた座標は該当行に控える (「Discord ピン投稿」節)。
- **行程**: Day ごとに時系列で書く。日程未定の間は Day 見出しを省いて「日程未定」と 1 行書く (決まっている要素があれば続けて箇条書きで残す)。Day 見出しの日付は行程が具体化した時点で付ける。
- **撤退基準**: 登山・ハイキングを含む旅行では省略しない。理由: 安全判断に直結する。カットオフライン (チェックポイント×時刻) は決行宣言までに確定させる。起点・ルート等の前提が未定なら案として記録する。即時撤退条件は雷鳴確認等、その場で引き返す条件。登山・ハイキングを含まない旅行では欄ごと削ってよい。
- **一時 cron 記録**: この旅行向けの一時 cron を仕込んだら、ジョブ名・発火時刻・対象日・プロンプト要点を 1 行で追記する。削除・再設定・障害と補填も記録する。理由: `once` ジョブは失敗しても定義ファイルが消えるため、この記録が補填内容を再現する唯一の手がかりになる。
- **装備**: 形態に該当しないサブセクションは削る。既定リストは出発点で、旅行固有の品と検討結果を足す。
- **予約・チケット / 緊急連絡**: ラベル行は残し、判明したものから埋める。
- **当日メモ**: 現地での気付き・変更事項を時系列で追記する。書き始めたら `status` を `ongoing` にする。
- **事後振り返り**: 旅行終了後に必ず埋める (手順は「事後振り返りの埋め方」節)。埋めたら `status` を `completed` にする。各欄の中身:
  - 実績ペース: 登山時はヤマレコのコースタイム比。倍率は `yamareco` skill (`.claude/skills/yamareco/SKILL.md`) の手順で算出する。
  - 装備の過不足: 不要だったもの・足りなかったもの。
  - 宿・移動・立ち寄り先の評価: 温泉・食事等を含む。
  - 満足度: 0〜5 の整数。道の駅・展望台等の立ち寄り先や道の混雑も含めて `AskUserQuestion` で確認する。
  - ユーザの反応・感想: Discord 発言・bluesky 投稿から拾えたもの。
  - 参照した知見の検証:「参照した知見」の各項目が効いたか外れたか。外れた場合は理由。
  - 次回への申し送り: リピート時の注意点・避けたい時間帯等。

## frontmatter の運用

ノートのメタ情報はファイル先頭の YAML frontmatter で管理する (OKF v0.1 準拠 + 独自キー)。値はすべて YAML string として書く。キーは次のとおり。

| キー                   | 書式                                                                                                           | 記入・削除の時期                                                      |
| ---------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `type`                 | `trip` 固定                                                                                                    | 作成時                                                                |
| `title`                | 旅行名                                                                                                         | 作成時                                                                |
| `status`               | `planning` / `scheduled` / `ongoing` / `completed` / `cancelled`                                               | 作成時は `planning`。遷移は下記                                       |
| `description`          | 概要を 1 文で                                                                                                  | 作成時                                                                |
| `destination`          | 行き先 (山名・地名と都道府県)                                                                                  | 作成時                                                                |
| `start_at` / `end_at`  | Day 1 の出発時刻 / 最終日の帰着時刻。ISO 8601 (オフセット必須)、引用符付き                                     | `scheduled` へ遷移する時点で両方。日程未定の間はキーごと書かない      |
| `tags`                 | 登山 / ハイキング / 観光 / キャンプ / バイクツーリング を基本に該当をすべて列挙 (収まらない形態は自由に追加可) | 作成時                                                                |
| `thread`               | Discord スレッド ID (snowflake)、引用符付き                                                                    | スレッドを立てた時点。無い間はキーごと書かない                        |
| `pin_channel`          | ピン投稿の投稿先チャンネル ID。snowflake、引用符付き                                                           | ピン投稿を作った時点 (「Discord ピン投稿」節)。全部ピン解除したら削除 |
| `pin_messages`         | スケジュール投稿のメッセージ ID の配列 (投稿順)。snowflake、引用符付き                                         | スケジュール投稿を作った時点。ピン解除したら削除                      |
| `pin_packing_messages` | もちもの投稿のメッセージ ID の配列 (投稿順)。snowflake、引用符付き                                             | もちもの投稿を作った時点。ピン解除したら削除                          |
| `timestamp`            | このノートの最終更新日時。ISO 8601 `+09:00`、引用符付き                                                        | 編集のたびに現在時刻へ更新                                            |

`start_at`/`end_at` の時刻が未記録・未確定の間の暫定値は、`start_at` が当日の `T00:00:00+09:00`、`end_at` が最終日の `T23:59:59+09:00` (単日で帰着未定でも同様。`end_at` が `start_at` より前にならないようにする)。確定時に実時刻へ更新する。

- `status` は旅行の状態:
  - `planning` (検討中・日程未定)
  - `scheduled` (日程確定・実施待ち)
  - `ongoing` (旅行中)
  - `completed` (実施済)
  - `cancelled` (中止・行かないことが確定)
- 遷移の契機:
  - 日程が確定したら `scheduled`
  - 当日メモを書き始めたら `ongoing`
  - 事後振り返りを埋めたら `completed`
  - 行かないことが確定したら `cancelled` (ノート自体は消さない)
  - 延期で日程が未定に戻ったら `planning` へ戻し、`start_at`/`end_at` を削除する。
- `scheduled` へ遷移するときは `start_at`/`end_at` を必ず記入する (ファイル名・スレッド名だけに日付を持たせない)。時刻が未確定の間は上記の暫定値を使う。
- `scheduled` へ遷移するときは、`memory/travel/PLANS.md` の出発準備・現地確認に関わる項目を「参照した知見」と突合し、抜けがあれば足す。
- ノートを編集したら必ず `timestamp` を現在時刻 (ISO 8601、`+09:00` オフセット付き) へ更新する。
- 日時 (`start_at`/`end_at`/`timestamp`) は必ず引用符付きの文字列で書く。スレッド ID の `thread` と、ピン投稿の ID の `pin_channel`・`pin_messages`・`pin_packing_messages` の各要素も同様に必ず引用符付きの文字列で書く。理由: 裸で書くと YAML の型自動推論で日付化・整数化して壊れる。
- `thread` を記入するのはスレッドを立てた時点。**同じ流れで `active: true` の設定も済ませろ** (「Discord スレッドの設定」節)。`thread` が入っているのに設定が漏れている状態を作るな。
- キーの並び順は `assets/NOTE.md` に合わせる。後からキーを足すとき (`start_at`/`end_at`・`pin_channel`/`pin_messages`/`pin_packing_messages` 等) も同じ位置に挿入する。
- 配列の `tags`・`pin_messages`・`pin_packing_messages` は `assets/NOTE.md` のとおり 1 要素 1 行の `- ` 形式で書き、`[ ]` の形式は使わない。旧テンプレートで作った既存ノートの `tags: [` はそのままでよい。
- 日程の真実源は frontmatter (`start_at`/`end_at`)。日程確定時に本文の行程まで書き直す必要はない。本文の行程は中身が具体化した時点で書き、Day 見出しの日付もそのとき付ける。

## Discord ピン投稿

ユーザはノートを読めないため、スケジュールは travel チャンネルにピン止めした投稿で常時見える形にする。投稿はスケジュール投稿 (必須) ともちもの投稿 (任意) の 2 種類で、本文の骨格はそれぞれ `assets/PIN-SCHEDULE.md`・`assets/PIN-PACKING.md`。書式と URL の規則はこの節が定める。Discord への送信・編集・削除・ピン止め・解除のコマンドは `discord` skill (`.claude/skills/discord/SKILL.md`) の「メッセージ送信」「自分の投稿の編集」「自分の投稿の削除」「ピン止め・解除」に従う。ここではその上に載せる運用だけを定める。

### 対象と投稿先

- 対象は `status` が `scheduled` または `ongoing` のノート。`planning` は対象外。
- 投稿先は travel チャンネル本体。スレッドには投稿しない。理由: チャンネルのピン一覧が「これからの旅行の一覧」として働く。スレッド内のピンはスレッドを開かないと見えない。
- 投稿は 2 種類。スケジュール投稿は対象ノートに必ず 1 組、もちもの投稿はユーザが求めたときだけ 1 組 (「もちもの」項)。組は 1 通以上のメッセージで、すべてピン止めする。
- 組の状態は frontmatter の `pin_channel`・`pin_messages`・`pin_packing_messages` で持つ (意味と書式は「frontmatter の運用」のキー表)。組が無い間はキーごと書かない。

### 本文の書式

スケジュール投稿は `assets/PIN-SCHEDULE.md`、もちもの投稿は `assets/PIN-PACKING.md` の形に従う。`<...>` は値プレースホルダ。本文は Discord の Markdown で、見出し記法 (`#`) は使わず太字で代用する。

- 見出し行: `title` と `start_at`/`end_at` の日付から作る。曜日は日本語 1 文字。通が複数になるときは末尾に `(k/n)` を付ける (例: `**稚内・宗谷岬** 2026-09-19 (土) 〜 2026-09-24 (木) (2/3)`)。1 通なら付けない。
- Day ブロック: ノートの「行程」の Day 見出しごとに 1 ブロック。行程に無い Day は作らない。行は時刻順に並べる。
  - 時刻は `HH:MM`。未定なら `—` を置く。
  - 1 行 1 地点または 1 移動。移動は `A → B` の形で書く。「移動」「宿泊」に書かれた内容 (フェリーの発着・宿のチェックイン) も、該当する Day の行として時刻順に混ぜる。
  - 予約番号・集合時刻・最終出発時刻のような当日に見る値は、同じ行の括弧内に短く書く。理由・検討経緯・過去の教訓は書かない。
  - 行の直下の行に URL を 1 本置く (規則は次項)。URL を付けない行 (フェリー乗船中・帰宅等) はそのまま。
- 更新行: 本文を組み立てた時刻 (`date '+%Y-%m-%d %H:%M'`)。
- もちもの投稿の見出し行: `**<旅行名> もちもの**` に同じ日付を続ける。`(k/n)` の規則はスケジュール投稿と同じ。
- もちもの投稿の本文: ノートの「装備」のサブセクション (共通、登山・ハイキング、キャンプ、バイクツーリング) ごとに太字の見出しを置き、品名だけを 1 行 1 品で書く。理由・日付・検討経緯・見送った品は書かない。更新行はスケジュール投稿と同じ。

### URL の規則

Google Maps URLs (https://developers.google.com/maps/documentation/urls/get-started) の書式を使う。

- 地点 (宿・港・観光地・道の駅等): `https://www.google.com/maps/search/?api=1&query=<緯度>%2C<経度>`
- 移動 (陸路): `https://www.google.com/maps/dir/?api=1&origin=<緯度>%2C<経度>&destination=<緯度>%2C<経度>&travelmode=<mode>`
  - `<mode>` はバイク `two-wheeler`、車 `driving`、徒歩・登山 `walking`、公共交通 `transit`。ノートの `tags` と「移動」の記述から選ぶ。
  - 経由地があれば `&waypoints=<緯度>%2C<経度>%7C<緯度>%2C<経度>` を足す (区切りは `|` をエンコードした `%7C`、最大 9 地点)。
  - フェリー・鉄道の区間には経路 URL を付けない。乗降する港・駅を地点として書く。
- 座標は小数 4 桁 (約 11 m)。理由: 住所文字列を URL エンコードすると 1 本 300〜600 文字になり、2000 文字の 1 通に数本しか入らない。座標なら 1 本 120 文字程度で済む。
- 座標の取得は国土地理院住所検索 API で行う (`jartic-traffic-volume` skill のジオコーディングと同じ API)。

  ```sh
  curl -sS -G 'https://msearch.gsi.go.jp/address-search/AddressSearch' --data-urlencode 'q=<住所または施設名>'
  ```

  - 応答の `geometry.coordinates` は `[経度, 緯度]` の順。URL には緯度・経度の順で入れる。
  - 候補が複数のときは `properties.title` を見て、ノートの都道府県・市町村に合うものを選ぶ。先頭を機械的に採らない。
  - ノートに住所があれば住所で引く (施設名より一意に決まる)。
  - 引けない、または「〜付近」のように地点が曖昧な場合は、その行だけ座標の代わりに地名・住所を URL エンコードして入れる。
  - 会話の中で引いた座標はノートの該当箇所 (「移動」「宿泊」等) に `(35.6812, 139.7671)` の形で控え、次回の更新で再利用する。
- ノート本文に住所ベースの経路 URL が既に書かれていても、ピン投稿にはそれを転記しない。上の規則で組み直す。

### 本文の組み立て

- 組ごとに別々に組み立てる。スケジュール投稿のブロックは「見出し行」「Day ごと」の順、もちもの投稿のブロックは「見出し行」「装備のサブセクションごと」の順。
- 1 通は 2000 文字以内 (`discord` skill の分割閾値と同じ数え方)。ブロックを順に足し、次のブロックを足すと超えるところで通を切る。1 ブロック単独で超える場合は箇条書きの境界で割り、後半の見出しに「(続き)」を付ける。
- 通が 2 つ以上のときは、各通の先頭を見出し行にして `(k/n)` を付ける。1 通なら付けない。
- 送信・編集の JSON は `jq -Rs '{content: ., flags: 4}'` で作る (`discord` skill の `{content: .}` に `flags: 4` を足す)。`4` は `SUPPRESS_EMBEDS` で、URL のプレビューを出さない。理由: 経路 URL ごとにプレビューが付くと投稿が縦に伸びる。

組み上がりの例 (`20260919-wakkanai-soya.md` の Day 1〜2。座標はプレースホルダのまま):

```text
**稚内・宗谷岬ツーリング** 2026-09-19 (土) 〜 2026-09-24 (木) (1/2)

**Day 1 (09-19 土)**
- 12:30 自宅 → 新潟港フェリーターミナル (最終出発 12:30、集合 21:30)
https://www.google.com/maps/dir/?api=1&origin=<緯度>%2C<経度>&destination=<緯度>%2C<経度>&travelmode=two-wheeler
- 22:30 新日本海フェリー らいらっく 新潟発

**Day 2 (09-20 日)**
- 16:45 苫小牧東港着
https://www.google.com/maps/search/?api=1&query=<緯度>%2C<経度>
- 18:30 苫小牧ホテル杉田 チェックイン (予約 4127)
https://www.google.com/maps/dir/?api=1&origin=<緯度>%2C<経度>&destination=<緯度>%2C<経度>&travelmode=two-wheeler

更新: 2026-09-08 23:40
```

### 作成・更新・終了

手順は組ごとに同じ。次の「該当キー」は、スケジュール投稿なら `pin_messages`、もちもの投稿なら `pin_packing_messages`。

- 作成の契機: スケジュール投稿は `scheduled` へ遷移したとき (対象なのに `pin_messages` が無いことに気付いたときも同じ)。もちもの投稿はユーザが求めたとき。
- 作成手順: 本文を組み立て、通ごとに送信して返ってきた `id` をピン止めする。全通の ID を該当キーに投稿順で書き、`pin_channel` が無ければ投稿先チャンネル ID を書く。
- 更新の契機: スケジュール投稿は、日程 (`start_at`/`end_at`)・行程・移動・宿泊・予約のいずれかをノートで変えたとき。もちもの投稿は、装備を変えたとき。どちらもユーザに求められたときも。
- 更新手順: 本文を全通ぶん組み直し、該当キーの ID を先頭から順に PATCH で全体置換する。応答の `pinned` が `false` なら PUT でピン止めし直す。組み直した通数が既存より多ければ、余りを送信 + ピン止めして配列の末尾に足す。少なければ余った既存 ID を DELETE し (削除でピンも消える)、配列から外す。
- PATCH が `404` を返したら (投稿が消されている)、その通を送信 + ピン止めで作り直し、配列の同じ位置の ID を差し替える。
- 終了: `status` を `completed`・`cancelled` にしたとき、または延期で `planning` に戻すとき、両方の組の全通をピン解除して `pin_channel`/`pin_messages`/`pin_packing_messages` を削除する。投稿は消さない。
- 週次の `travel-digest` cron が、対象なのにスケジュール投稿が無いノートの作成と、対象外なのにキーが残るノートのピン解除 (両方の組) を補う。会話の中で変えた分を cron に任せて放置しない。

### もちもの

- もちもの投稿はユーザが求めたときだけ作る。スケジュール投稿に混ぜない。理由: 1 通が長くなる。
- 一度作ったら、装備を変えたときに更新する。外せと言われたら全通を DELETE して `pin_packing_messages` を削除する。

### 返信との関係

ピン投稿を作成・更新したら、返信にその旨を 1 行添える。ピン投稿は返信の代わりではない。返信に載せる内容は「Discord 返信との関係」節に従う。

### 権限

ピン止めには bot に `PIN_MESSAGES` 権限が要る (`discord` skill の「ピン止め・解除」)。PUT が `403` を返したら、投稿は残したまま ID を該当キーに書き、返信で権限不足を伝える。次回の更新手順の `pinned` チェックで再試行される。

## 記入ルール

ノートのどの欄も、取得できなかった値を捏造するな。拾えない欄は空欄のままにするか「不明」と書け (この捏造禁止は全欄に適用する。事後振り返りの見積もりに限らない)。

## 過去ノートの参照

- 全体像は `memory/travel/index.md` を見る (status 別一覧 + 直近の旅行サマリ。cron ジョブ travel-digest が週次で自動生成)。
  - index.md は自動生成物なので手で編集しない。
  - ノートを更新しても index.md への反映は不要 (週次 cron が追従する)。
  - 初回生成前は存在せず、それ自体は異常ではない。
  - 存在しない場合は次の `ls memory/travel/` の手順で代替する。
- 次回計画時は `ls memory/travel/` + 該当ファイルを `cat` して参照する。
- ステータスや日程での絞り込みは frontmatter を使う (例: `grep -l "^status: planning" memory/travel/*.md`)。
- 形態や行き先での絞り込みも frontmatter を使う。行き先は `grep -l "^destination:.*丹沢" memory/travel/*.md`。`tags` は要素が別行にあるため frontmatter 内の要素行を見る (例: `awk '/^---$/{n++} n==1 && /^  (- )?登山,?$/{print FILENAME; nextfile}' memory/travel/*.md`。旧テンプレートの `tags: [` 形式の要素行 `  登山,` にも当たる)。ヒットしたノートは「事後振り返り」だけ読めば足りる。

## 事後振り返りの埋め方

旅行終了後、ノートの「事後振り返り」欄を埋める。材料は複数ソースから集める。

- `bluesky` skill … ユーザの行動は bluesky に投稿されていることが多い (「○○に行った」等の結果報告)。アカウントは `.claude/rules/user.md` 参照。
- **登山だった場合は `yamareco` skill でユーザの山行記録 (実績) も確認する。** 実際のコースタイム・ペースを取得し、事前見積もりとの差を旅行ノートに残す (次回計画のペース倍率に効く)。
  - 帰宅当日は山行記録がまだヤマレコに登録されていないことが多い。該当する記録が無く bluesky にも結果報告が無ければ、実績欄は「実績未取得 (記録登録待ち)」とし数値を捏造しない。記録登録の有無をユーザに確認し、後日上がってから振り返りを再実行する。
  - 事前見積もりが旅行ノートに無い場合 (帰宅時に初めてノートを作る等) は、ヤマレコの登録済み登山計画を見積もりの代理に使う。登録済み登山計画は予定倍率・計画タイムを指す。
  - それも無ければ実績のみ残し「事前見積もり無し」と明記する (値を捏造しない)。

対応する旅行ノートが無い場合 (ノート規約以前に立てたスレッド、またはスレッドを立てなかった日帰り等) は「新規作成」の手順でノートを作ってから埋める。ファイル名は出発日に揃える (スレッドがあればスレッド名の先頭日付と一致する)。

- **bluesky 等での情報集約後、拾いきれなかった点や解釈が割れる点は `AskUserQuestion` でユーザに確認する。** 材料収集は自動化するが、埋める前に不明点を残したまま憶測で埋めない。ユーザと対話できる文脈 (帰宅報告への応答等) では、確認できずに「次回への申し送り」へ先送りする前にまず聞く。
- **行き先 (道中の立ち寄り先: 道の駅・展望台・食事処等、道の混雑度も含む) の満足度を 0-5 の整数でユーザに `AskUserQuestion` で確認する。** 複数の立ち寄り先がある旅行では、代表的なもの (または全体としての満足度) を確認してよい。取得した値は「事後振り返り」の「満足度」欄に記入する。
- **「参照した知見の検証」を必ず埋める。**「参照した知見」の各項目について効いたか外れたかを書き、外れた項目は理由を添えて「次回への申し送り」にも書く。1 行に複数の要素がある項目は要素ごとに判定する。旅行の前提と合わず当否を判定できない要素は「適用外」と書く (効いた・外れたのどちらにも数えない)。理由: travel-digest が PLANS.md を直す材料にする。

振り返りを実行したら振り返り欄に空欄を残さない。拾えなかった欄は「不明」と書く (空欄 = 振り返り未実行、と区別するため)。形態上そもそも存在しない項目 (日帰りの宿泊等) は「不明」でなく「該当なし」と書く。判明した情報がどの欄にも収まらない場合は最も近い欄に書く (複数欄への重複記載も可)。ユーザに確認が必要だが確認できない文脈では、確認事項を「次回への申し送り」欄に残し、次に対話できるタイミングで確認する。

埋め終えたら `status` を `completed` に、`timestamp` を現在時刻に更新する。実績が未取得でも、全欄を「不明」「実績未取得 (記録登録待ち)」で埋めた時点で `completed` に遷移してよい。後日の再振り返りは `completed` のまま該当欄を上書きし、`timestamp` を更新する。
