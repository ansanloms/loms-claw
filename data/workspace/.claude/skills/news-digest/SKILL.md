# ニュース収集・要約

指定テーマの最新ニュースを優先ソースから集め、各記事を要約して返す手順。収集と要約のコアのみを担い、重複チェックの取得手段や最終的な整形・投稿は呼び出し側に委ねる。出力は特定の媒体に依存しない中立フォーマットとする。

## 引数

| 引数       | 既定値 | 説明                                                                                                               |
| ---------- | ------ | ------------------------------------------------------------------------------------------------------------------ |
| テーマ     | (必須) | 収集対象の説明 (例: バイク関連の最新ニュース・新車情報・イベント)。                                                |
| 優先ソース | (任意) | 優先的に探すドメイン・RSS のリスト。無ければ一般 Web 検索。該当が無ければ他ソースを探し固執しない。                |
| 件数       | 3      | 集める記事数。                                                                                                     |
| 期間       | (任意) | 対象期間 (例: 直近 5 日)。指定時はそれより古い記事を除外する。無指定なら期間フィルタを適用せず全期間を対象とする。 |
| 除外リスト | (任意) | 既出記事のタイトル・URL。呼び出し側が重複チェックで得たものを渡すと、結果から除外する。                            |

引数はキー名 (テーマ・優先ソース・件数・期間・除外リスト) を明示した自然文で渡す。例えば「テーマ: バイクの新車情報、優先ソース: (なし)、件数: 3、期間: 直近 5 日、除外リスト: (直近投稿分のタイトル・URL)」のように、キーと値の対応が分かる形で指定する。

## 全体フロー

1. 優先ソースを確認する。RSS/Atom フィードがあれば一般 Web 検索より先にフィードを取得する。フィードは新着順なので新しい記事の概要をつかみやすい。取得手段は次項「取得手段」を参照。
2. 優先ソースに該当記事が無い、または RSS/Atom の取得自体に失敗した場合は他ソースを探す。優先ソースに固執せず、一般 Web 検索や別ドメインへ広げてよい。優先ソースはあくまで第一候補である。
3. 候補を次の順でフィルタし、満たさない記事を落とす。
   - テーマ適合: 依頼テーマに合うか。総合ニュースサイトなど雑多なソースからは無関係な記事を除く。
   - 期間: 期間指定があれば範囲内か。基準は実行日 (今日) を起点に遡る (例: 直近 5 日なら今日から 5 日前まで)。実行日は `TZ=Asia/Tokyo date +%Y-%m-%d` で取得した日本時間の日付を使う (ホスト側のタイムゾーン設定に依存させないため)。公開日は各記事の個別ページ (次項「取得手段」参照) で確認し、フィードや検索一覧の日付と食い違う場合は個別ページを優先する。個別ページが取得できない (403 等)、または取得できても本文が JS レンダリング等で欠落し日付・要約の根拠にできない場合は、(1) 取得できた HTML 内の構造化メタデータ (`datePublished` 等) やページ本文の明示的な日付表記 (byline 等) を確認、(2) 同一の出来事を報じる検証可能な別媒体の記事に差し替え、(3) いずれも不能なら候補から除外、の順で対処する。
   - 除外リスト: 除外リストのタイトル・URL に一致しないか。文字列一致だけでなく、除外リストの記事と同一の出来事を報じる別ソースの記事も既出として除外する (手順 4 の重複判定と同じ基準を除外リストとの照合にも適用する)。除外記事のタイトルが通称のみで出来事を特定できない場合は、検索等で識別子 (CVE・製品名・組織名等) を特定してから候補と突き合わせる。
4. 残りから件数分を選び、各記事を要約する。確認した公開日で新しい順に選ぶ (ソースごとに件数を固定配分しない)。ただしテーマに「注目」「重要」等の重み付け語が含まれる場合は、重要度をテーマ適合の判定に含め、同格の候補内でのみ新しい順を適用する (定型のリリース記事が新しさだけで重大事案を押し出さないようにする)。同格の階層は「実被害の確認済み > 実悪用の観測 > PoC・脆弱性公表のみ > 定型リリース・アップデート」を目安とする。同じ記事や、同一の出来事 (同一バージョンのリリース等) を指す別ソースの記事は重複として 1 件にまとめ、情報量の多いものを採る。件数に満たなければ無理に埋めない (扱いは「出力」を参照)。

### 取得手段

- RSS/Atom フィード: `curl -sL -A "<UA>" "<フィード URL>"` で XML を直接取得する。UA には次の値を使う (個別記事ページの取得でも同じ値を使う)。

  ```
  Mozilla/5.0 (compatible; news-digest-skill/1.0; +https://github.com/ansanloms/skills)
  ```

  取得した XML は専用パーサを介さず、テキストとしてそのまま読んで項目を拾う。RSS 2.0 は `<item>` ごとの `<title>`・`<link>`・`<pubDate>`・`<description>`、Atom は `<entry>` ごとの `<title>`・`<link href="...">`・`<updated>` または `<published>`・`<summary>` を見る。
- 個別記事ページ (公開日確認・要約根拠の取得): `curl -sL -A "<UA>" "<記事 URL>"` で HTML を直接取得し、返ってきたテキストをそのまま読んで本文・日付を確認する。RSS/Atom と同じ UA を使い、WebFetch は使わない。理由は RSS/Atom で curl を選んだ理由と同じで、AI による要約変換を介さず取得内容をそのまま扱うことで、数値 (CVSS・計測値等) の変換過程での誤りを避けるため (「ルール/注意」の数値の扱いを参照)。取得できない、または本文が取得できず日付・要約の根拠にできない場合は上記「期間」の (1)〜(3) のフォールバックに従う。
- 一般 Web 検索: WebSearch でテーマに関するキーワードを検索する。次のいずれかに該当する場合にこの手段へフォールバックする。
  - 優先ソースが指定されていない。
  - 優先ソースはあるが RSS/Atom の URL が無い、または不明である。
  - RSS/Atom の取得を試みたが、HTTP エラーやタイムアウトで失敗した。
  - RSS/Atom は取得できたが、テーマに合致する記事が無かった。

## 出力

記事ごとに次の 4 項目を、`**ラベル:** 値` の形式で 1 記事につき 4 行にまとめて返す。ラベルは日本語 (タイトル・要約・公開日・個別 URL) を使う。`**` によるラベルの太字はこの書式そのものであり、除去しない。複数件を返す場合は、この 4 行ブロックを記事ごとに空行で区切って並べる。ラベルの太字以外の媒体固有の記法 (Discord の見出し記法・メンション・カスタム絵文字・チャンネルリンク等) は付けない。整形は呼び出し側が行う。

| 項目     | 内容                                                         |
| -------- | ------------------------------------------------------------ |
| タイトル | 記事の見出し。                                               |
| 要約     | 300 文字程度。何が起きたか・要点が分かる粒度にする。         |
| 公開日   | `YYYY-MM-DD` 形式。記事自体の公開日 (製品の発売日ではない)。 |
| 個別 URL | その記事のページ URL。                                       |

### 出力例

実際に取得した記事 1 件を、この書式に当てはめた例を示す (取得日: 2026-08-10、優先ソース: GIGAZINE の RSS)。

```
**タイトル:** CloudflareがAIエージェント向けブラウザ「Kitesurf」をリリース、ChromiumよりCPU・メモリ消費を大幅削減
**要約:** Cloudflare は、AI エージェント専用のブラウザ「Kitesurf」を発表した。タブや拡張機能など人間向け機能を省き、Cloudflare Workers 上の V8 アイソレートで動作する設計とし、AI エージェントがウェブページを読み取り・操作する際の CPU・メモリ消費を抑えることを優先している。実際に 14 個の URL で 5 回ずつ計測した結果、スクリーンショット取得時の CPU 使用時間は Chromium の 1173 ミリ秒に対し 380 ミリ秒、メモリ使用量も 271.0MiB から 57.8MiB まで削減されたという。一方で処理完了までの所要時間は現状 Chromium の方が短く、今後の改善課題として挙げている。
**公開日:** 2026-08-10
**個別 URL:** https://gigazine.net/news/20260810-cloudflare-kitesurf/
```

件数を満たさず 1 件以上見つかった場合は、無理に件数まで埋めようとせず、条件を満たした分だけをそのまま (不足を示す特別な注記は付けずに) 返す。該当記事が無ければ (取得はできたが対象記事が 0 件の場合)、件数分を埋めようとせず「該当なし」とだけ返す。RSS/Atom の取得失敗や全ソースへの到達不能など、情報を得ること自体に失敗した場合は「該当なし」と区別し、`取得失敗: <理由>` の形式で理由を添えて返す (例: `取得失敗: 優先ソースの RSS 取得が 404、Web 検索でも関連記事が見つからず`)。

## ルール / 注意

- URL は個別記事のページを貼る。サイトのトップページや一覧ページの URL は不可。個別 URL がどうしても取れない場合のみ URL を省略し、省略した旨を添える。
- 要約は 300 文字程度を目安とする。短すぎて要点が欠ける、長すぎて冗長になる、のいずれも避ける。要約は個別記事ページから取得した内容に基づいて書く。検索結果の要約スニペットのみを根拠にしない (数値の誤りが混入する)。数値 (CVSS 等) が媒体間で食い違う場合は採用した記事の値に合わせる。
- 個別ページ取得のフォールバック (期間の項の (1)〜(3)) は日付確認に限らず、要約根拠の取得など個別ページ取得全般に適用する。
- 該当ゼロと取得失敗の区別は「出力」の該当箇所に従う。いずれの場合も記事・日付・URL を捏造しない。公開日が不明なら不明と明示し、推測で埋めない。
- 前置き・挨拶・締めの言葉は不要。記事の並びだけを返す。

## 呼び出し側での整形 (参考)

この skill は中立フォーマットで記事を返すだけで、媒体ごとの整形・投稿は行わない。呼び出し側 (例: Discord の #news へ投稿する cron) は次のように使う。

1. 重複チェック: 投稿先の直近の記事一覧を自前の手段で取得する (既出のタイトル・URL)。
2. この skill を呼ぶ: テーマ・優先ソース・件数・除外リスト (直近の既出分) を引数として渡す。
3. 整形・投稿: 返ってきた記事を媒体の記法 (Discord なら見出し・要約・公開日と URL の行) に整形し、まとめて投稿する。「該当なし」なら投稿しない。`取得失敗: <理由>` が返った場合は該当なしと同一視せず、投稿を見送るだけでなく運用者に分かる形で失敗を記録・通知する。

中立フォーマットにしている理由は、投稿先や記法が呼び出し側ごとに異なるためである。整形まで skill に固定すると媒体を増やすたびに分岐が増えるので、収集と要約までを共通化し、整形は呼び出し側に残す。
