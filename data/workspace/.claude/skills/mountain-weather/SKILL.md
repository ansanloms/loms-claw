# 山の天気の判断

登山対象の山の天気を、登山指数・麓の気象・山頂標高指定の数値予報・標高差からの推定で総合的に判断する手順。

## scripts ディレクトリの絶対パスを確定する

この skill の主軸 4 コマンド (`find-mountain` ・ `fetch-index` ・ `find-area` ・ `fetch-openmeteo`、いずれも後述) は `mountain-weather/scripts` を `--cwd` に指定して実行する。パスは変数に代入せず、最初に 1 度だけ次のコマンドで絶対パスを確定し、以降の各コマンド例ではその結果をそのままリテラルで書き下す。理由: エージェントのシェルはコール間で cwd ・変数を失う (詳細は「2. 気象庁の麓の天気」の DANGER 参照)。

```sh
for d in "$PWD/.claude/skills/mountain-weather" "$HOME/.claude/skills/mountain-weather" "$PWD/mountain-weather"; do
  if [ -d "$d/scripts" ]; then
    echo "$d/scripts"
  fi
done
```

- 配布先 (`apm install` 後) では、プロジェクトローカルな配置の `$PWD/.claude/skills/mountain-weather/scripts` またはユーザレベルな配置の `$HOME/.claude/skills/mountain-weather/scripts` がヒットする。
- この skill のリポジトリ本体 (`ansanloms/skills`) 内で作業している場合は `$PWD/mountain-weather/scripts` がヒットする。
- 複数ヒットしたら先に見つかったものを使う。0 件のときは、実際のインストール先を確認してから進める (推測でパスを組み立てない)。理由: 想定した配置になっていない。
- 以降のコマンド例中の `<scripts の絶対パス>` は、ここで確定した絶対パスに読み替える。呼び出すたびにこのパスをリテラルで書き下し、変数には入れない。
- `scripts/README.md` (内部動作の参照先として各節から案内する) のコマンド例はすべて `--cwd` 無しで、cwd が `scripts` ディレクトリ自身である前提で書かれている。この SKILL.md と併読するときも、実行時は必ずここで確定した絶対パスを `--cwd` に付ける (`scripts/README.md` の例をそのままコピーしない)。

## 前提: 何が取れて何が取れないか

山頂のピンポイントな気象数値そのものは一般に保証されないが、判断材料となる指標は無料で取得できる。

| ソース                              | 取得方法                                   | 中身                                                                                             | 山頂相当か                              |
| ----------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------ | --------------------------------------- |
| てんくら (`tenkura.n-kishou.co.jp`) | `fetch-index` script (無料のサーバ HTML)   | 登山指数 A/B/C (今日・明日は時間帯別、約 1 週間分)、気圧面ごとの気温・風                         | 山ごとの独自指数 (山頂を含む予報ベース) |
| 気象庁 (JMA)                        | curl + jq (無料の JSON)                    | 麓・登山口を含む細分区の天気・風・降水確率、麓のアメダス地点の気温                               | 麓・地域レベル                          |
| Open-Meteo (`api.open-meteo.com`)   | `fetch-openmeteo` script (無料の JSON API) | 山頂標高指定の気温・湿度・風・突風・降水・降水確率・凍結高度・天気コード (1 時間ごと、最大 7 日) | 標高補正済みの NWP (数値予報) 値        |

判断の主軸はてんくらの登山指数とし、気象庁で麓の実データを、Open-Meteo で山頂標高指定の数値予報を併せて見る。

### 例外: 富士山だけは山頂の実測気温が取れる

気象庁アメダスの `50066` (地点名「富士山」、標高 3775m) は山頂に設置されており、気温を観測している。富士山を扱うときはこれを山頂気温の実測として使える。3775m はこのアメダス観測点の標高で、富士山の最高地点である剣ヶ峰の公称標高 3776m (「3.」の Open-Meteo の例で使う値) とは測点位置が異なる別の値。1m の差は誤記ではない。

ファイルは 3 時間ごとに分かれ、1 ファイルがその 3 時間を覆う。`<hh>` は `00/03/06/09/12/15/18/21` のいずれかで、現在時刻を切り捨てた側を選ぶ (例: 20:45 の値が要るなら `_18`。`_21` はまだ生成されていない)。

```sh
# 取得日: 2026-08-10 (JST)。12 時ブロック (12:00〜14:50 を覆う) をブロック開始直後に取得した実物
# (そのため下のサンプルは 12:00・12:10 の 2 レコードのみで、ブロックの残り時間分はまだ無い)
curl -s "https://www.jma.go.jp/bosai/amedas/data/point/50066/20260810_12.json"
```

```jsonc
{
  "20260810120000": {
    // 毎正時のレコードには温度以外の要素も入る
    "pressure": [647.0, 0], // [値, 品質フラグ]。フラグ 0 = 正常
    "temp": [6.0, 0],
    "humidity": [14, 0]
    // snow1h/6h/12h/24h, sun10m, sun1h, maxTempTime, maxTemp, minTempTime, minTemp, gustTime は省略
  },
  "20260810121000": {
    // 毎正時以外は humidity・pressure のキー自体が無い (temp 以外の要素は残る)
    "temp": [5.8, 0]
    // sun10m, sun1h, maxTempTime, maxTemp, minTempTime, minTemp, gustTime は省略
  }
}
```

- この skill が使う `temp`・`humidity`・`pressure` は `[値, 品質フラグ]` の 2 要素配列で返る。スカラーではない。
  - レコード内の全キーがこの形とは限らない。`maxTempTime`・`minTempTime`・`gustTime` はオブジェクト、`prefNumber`・`observationNumber` は素の数値。
  - 「非 `null`」の判定は要素キーの有無ではなく `temp[0]` (値本体) が `null` かどうかで行う。`temp[1]` は品質フラグで、値の有無の判定には使わない。
- レコードのキーは `yyyymmddHHMMSS` で、時刻順にソートした最後の要素が最新値。
- 要素ごとに配信粒度が違う。`temp` は 10 分ごと (3 時間で 18 レコード)、`humidity` と `pressure` は毎正時のみ。
  - 粒度を一律と決め打ちせず、必要な要素が入っているレコードを選ぶ。
  - 上のサンプルのとおり、毎正時以外のレコードには `humidity`・`pressure` のキー自体が存在しない (`null` が入るのではない)。
- MUST: ブロックの選択は HTTP ステータスだけで決めない。必要な要素が非 null で入っているレコードがあるかまで確認する。
  - 切り捨て側のブロックが HTTP 200 で返っても、配信ラグにより最新レコードに `temp` が入っていないことがある (毎正時ちょうどに引いた場合に起きやすい)。
  - その場合はさらに 1 つ前のブロックへ下げて引き直す。ファイルをまたいで下げてよい。
- MUST: 未到来の時間ブロックを引くと HTTP 404 で `text/html` が返る。
  - 理由: これは異常系ではなく「そのブロックがまだ生成されていない」だけ。取得失敗として処理を止めない。切り捨て側のブロックへ下げて引き直す。
  - `jq` に素通しせず HTTP ステータスを先に見る。理由: JSON パースエラーで落ちる。
  - この 404 は、他の取得失敗 (止めて報告する対象) と区別する。

  取得日 2026-08-10 13 時台 (JST) に、まだ始まっていない 15 時ブロックを実際に叩いて確認した実物は次のとおり。

  ```sh
  # 取得日: 2026-08-10 13:24 JST (15 時ブロックは開始前)
  curl -sS -D - -o /dev/null "https://www.jma.go.jp/bosai/amedas/data/point/50066/20260810_15.json"
  ```

  ```text
  HTTP/2 404
  content-type: text/html
  content-length: 2203
  ...
  ```

  本文は JSON ではなく `<title>404｜気象庁</title>` を含む HTML ページ。ステータス行と `content-type: text/html` だけで判定でき、本文をパースする必要はない。
- 使いどころは 2 つ。過去・現在の実況として山頂気温を答えること、および予報の当たり外れを事後に確認すること。
- MUST: 風は観測していない。レコードに `wind` キー自体が存在しない (`null` が入るのではない。`null` を期待した参照はエラーになる)。
  - 風は他の山と同じくてんくらの気圧面風を主に扱う。理由: 富士山でも山頂の風の実測は取れない。
  - この「気温だけ実測が取れる」非対称を、風にも実測があるかのように書かない。
- 実測は予報ではない。予報の代替にはならない。理由: 未来の時刻の値は当然取れない。
  - 取得できるのは既に経過した時刻の値だけ。
- 他の山にこの地点の値を流用しない。標高 3775m の値であり、他山の山頂気温とは無関係。標高 1000m 以上のアメダスは他にもある (御嶽山 2195m、上高地 1510m 等)。
  - 流用前に地点一覧と実データの `temp[0]` が `null` でないかを確認する。理由: 多くは気温を観測しない地点。地点一覧は `https://www.jma.go.jp/bosai/amedas/const/amedastable.json` の対象地点 `elems` フィールド (「4.」の基点標高の項で使うのと同じファイル)。
  - `elems` は各地点が観測する要素を表す 8 桁の 0/1 文字列だが、`elems` だけで判定を確定させない。理由: 桁位置と要素の対応は公開ドキュメントで確認できない。最終的には実際のレスポンスに `temp` キーが存在し値が `null` でないかで確認する。

## 限界をユーザに伝える

- てんくらの登山指数 (A/B/C) は同社が独自基準で算出した指標であり、山頂の実況気象そのものではない。気象庁データは麓・地域レベルで、山頂とは乖離しうる。
- 山は標高・地形で天気が急変する。麓が晴れでも山頂は強風・荒天ということが普通に起きる。指数や麓の予報を山頂の確定予報のように断定して伝えない。
- 標高差から算出する山頂気温などは推定であると明記する。判断に迷う場合は危険側 (寒い・荒れる前提) に倒し、暖かい・穏やかな下振れに丸めて軽装・強行を促さない。
- Open-Meteo の値は数値予報モデルの生値を山頂標高で補正したものであり、予報士による検証を経ていない。地形性の局地風・雷・急変の読みは載らない。てんくらの登山指数を主軸とする判断構造は変えない。
- Open-Meteo の風速は格子平均地形上の 10m 風であり、稜線・山頂の地形による風の加速は反映されず過小になりうる (標高補正の主対象は気温で、風は補正されない)。風は参考値として「実際はこれより強い」前提で扱う。風の取得元の主体と強い側の採り方は「4.」の風の規則に従う。

### 無料ソースでは埋まらない穴

次の 3 つは、このソース構成では原理的に取得できない。取れないことを認識し、必要な場面では「この skill では判断できない」と明示してユーザに委ねる。取れないものを推測で補って答えない。

- 快晴・微風時の山頂地表の日射加熱。岩稜・岩峰の山頂は日射で地表付近が暖まるが、てんくらの気圧面気温は自由大気の値でこれを持たず、Open-Meteo も格子平均のため岩峰単位の加熱を表現しない。
  - 快晴かつ微風かつ岩がちの山頂では、日中の実際の気温が算出値を数度上回ることがある。この外れは暖かい側なので低体温の評価では安全側に倒れるが、夏の暑熱・熱中症の評価では危険側に外すことになる。
  - 該当条件では暑熱側のリスクを算出値だけで否定しない。
- 派生ハザード。沢の増水・登山道のぬかるみ・落石・雪渓の状態などは、降水量の数値から人が解釈して初めてハザードになる。
  - 降水量・降水確率は取れるが、そこから具体的なハザード名への変換はこの skill では行わない。
  - 前日・当日の降水量を提示したうえで、沢筋・徒渉のあるルートでは増水の可能性を別途確認するよう促すに留める。
- 危険度の言語化。予報士が書く「日中は真冬並みの気温、防寒・防風対策は万全に」のような、数値を人の行動指示へ翻訳した警告は出せない。
  - 数値と指数は提示できるが、それが例年比・季節比でどれほど異常かの位置づけは持たない。
  - 異常さの断定を避け、数値そのものと安全側の解釈を伝える。

## DANGER: 値がズレると危険なので慎重側に倒す

山の気象判断は安全に直結する。指数・気温・天気を実際より楽観的に (良い指数・暖かい・穏やか) 報告した結果、ユーザが軽装・強行で入山して事故った場合の被害は甚大である。次のガードレールを必ず守る。

- 下振れ方向への丸めは禁止する。不確実な値は危険側に倒す。
  - 危険側の向きはリスクごとに決まり、寒い側固定ではない。向きの決め方 (風は他要素と反転条件が異なる点を含む) は「4.」の手順 1 に集約してあるので、そこを参照する。
  - 良い方向への切り上げ・楽観はしない。
  - 雲量・眺望 (ご来光が見えるか等) は危険側に倒す対象ではなく、両論併記で断定を避ける。理由: 安全リスクでなく目的達成のリスク。
- 推測で値を埋めない。取得できない・確度が低いときはその旨を明示し、安全側で伝える。
- 複数ソース (てんくら・気象庁・Open-Meteo・推定) が食い違うときは楽観側を採らない。悪い方の見立てを主に置き、両方を併記する。
  - Open-Meteo の標高指定気温とてんくらの気圧面気温が食い違う場合も同じ原則に従い、寒い・強風・荒天側を主に置く。比較は同一時刻 (または同一時間帯) の値同士で行う。
  - 粒度が違う値 (時間別と日単位など) を突き合わせるときは、細かい側の値が粗い側の期間内で悪くなる時間帯を特定し、その時間帯を悪い側として併記する。
- 山頂気温は逓減率と風の影響で寒い側に寄せる (後述「山頂気温の概算」と接続)。氷点下・強風・発雷・荒天の兆候は省略せず必ず強調する。
- 登山指数は二値ではなく、A = 安全と読み替えない。指数は降水量・風速・雲量ベースで暑熱を主に見ておらず、指数 A でも夏の低山などでは熱中症のリスクがある。
  - 逆に指数 C でも樹林帯の登山道では雨・風の影響が小さいことはあるが、これは楽観の根拠にしない。
  - C は荒天前提で扱い、軽装・強行を促さない (良い側の非対称: 悪い含意は残し、良い含意は判断材料にしない)。
- 最終判断はユーザに委ねる。skill 側で「行ける」「問題ない」と断定しない。中止・撤退・日程変更の選択肢を常に残す。

## 1. てんくらの登山指数 (主軸)

登山指数 A/B/C の取得・抽出は `scripts` の `fetch-index` に、山コードの検索は `find-mountain` に集約してある (後述)。`kad.html` ・ `kasel.html` を手で `curl` ・ `iconv` ・ `grep` して自前パースしない。この禁止は登山指数・気温・風の抽出に限る。山の同定のために kad.html の標高・近隣市町村の表記を手で確認するのは可 (次節)。

登山指数はてんくらの公式定義で「登山をするための快適さを、山頂や山麓の気象条件から気象学的知見を用いてレベル値で表現した指数。降水量・風速・雲量などを総合的に考慮して独自計算したもの」とされる。数値の気象要素そのものでなく指数として出すのは、気象業務法により無料での山の天気予報の掲載が禁じられているためで、指数は山頂の予報から算出した目安にすぎず、山頂の実況気象そのものではない。

指数の性質は運営元への取材記事 (<https://yamahack.com/4594>) で次のとおり補強されている。判断に織り込む。理由: 読み違えると楽観に倒れる。

- 指数は「指定時間帯の山頂の天気」の判定で、登山口・ルート上の天候は反映されない。麓が雨でも山頂が雲の上で晴れなら A がありうる。だから気象庁の麓データとの併用 (「2.」) は必須で、指数 A を「ルート全体が良い」と読まない。
- B と C の差は雨が降る確率ではなく、雨・風の強さの度合い。「B = 降らないかもしれない、C = 確実に雨」という読みは誤りで、B でも基準値以上の雨・風が予想されている。
- 局所的な発雷の可能性は指数に入っていない。指数 A でも雷リスクは別途評価する (「2.」の発雷の項)。
- 梅雨・前線・台風の時期は前線位置のわずかな変化で天気が大きく変わり、予報が当たりにくい。この時期は指数の確度を落として扱い、直前 (前日・当日朝) の取り直しを必ず案内する。
- 的中率は検証されていない (山頂に測定器が無く検証不能、と運営元)。指数を確率的な保証として扱わない。

### 山のコードを引く

対象の山の名前から、てんくらの山コード (`kad.html?code=` の数値) を `find-mountain` で引く。skill 内のキャッシュ (`assets/tenkura-mountains.json`。全 9 地域の山リスト `kasel.html` から生成済み) を検索するのでネットワーク不要。

```sh
# -q はタスクランナーのバナー抑止 (出力を jq 等で機械処理するため。全 scripts 共通)
deno task -q --cwd "<scripts の絶対パス>" find-mountain --name=旭岳
# => {"matches": [{"code": "01150010", "name": "大雪山・旭岳", "ba": "hk", "pref": "北海道"}, ...]}
```

- 検索は部分一致。0 件のときは `--update` でキャッシュを取り直してから再判断する (山リストの更新頻度は低いが、新規追加・改名はありうる)。理由: exit 1 で止まる。
  - `--update` はスクリプトが各エントリの `ba` echo を照合し、CDN キャッシュによる別地域の混入を弾く。
- `pref` はコード先頭 2 桁の都道府県。地域は `ba` (`hk` 北海道/`th` 東北/`kk` 関東・甲信/`hr` 北陸/`tk` 東海/`kn` 近畿/`cg` 中国/`sk` 四国/`ks` 九州・沖縄)。

- 重複には 2 種類あり、扱いが違う。先にどちらかを見分ける。
  - (i) 同名だが別の山 (別の山域の同名峰)。下の同定手順で 1 つに絞り、絞れなければユーザに確認する。
  - (ii) 同一の山頂が複数県のエントリに分かれている (県境の山。例: 富士山山頂は山梨側 `19150004` と静岡側 `22150003` の 2 エントリがある)。絞る必要がなく、ユーザ確認の対象にもしない。理由: どちらも正しい山頂。
  - (ii) の場合は両方のコードで取得し、値が一致すればどちらを使ってもよい (回答には両方のコードを識別キーとして併記する)。食い違ったら悪い側 (指数が悪い・寒い・風が強い) を採り、両者の値を併記する。
  - この解決は要素ごとに行う (指数は指数どうし、気温は気温どうしで悪い側を採る)。悪い方のエントリを丸ごと選ぶのではない。
  - 対象日が週間部に入るときは必ず両方を突き合わせる。理由: 今日・明日の時間帯別は一致しても週間部だけ食い違うことがある。
- 同名の山が複数あることがある (例: 別の山域の同名峰。「旭岳」は北海道と福島県の両方に居る)。`pref` や標高で対象を確定する。
  - 同県に同名の山頂候補が複数あるときは kad.html (`https://tenkura.n-kishou.co.jp/tk/kanko/kad.html?code=<code>&type=15`) を取得し、ページ表記の標高・近隣市町村で確定する。理由: `find-mountain` の出力は標高を持たない。ページは Shift_JIS なので、iconv で UTF-8 化して見る。
  - 一意に定まらなければユーザに確認する。憶測で 1 つに決めない。
  - 候補をユーザに提示するときは、`pref` ・ `code` を識別キーとして列挙し、通称への変換は推測しない。
- リストには山頂以外の地点も混じる (`赤岳鉱泉` `赤岳山荘` `旭岳石室` など)。名前が `山荘` ・ `小屋` ・ `ヒュッテ` ・ `石室` ・ `鉱泉` ・ `温泉` などの施設語で終わる項目は山頂候補と分けて扱う。
  - 同じ山に `富士山山頂` ・ `富士山北麓5合目` ・ `富士山吉田口8合目` のように複数の地点エントリがあるときは、山頂の気象判断には `山頂` を含むエントリを主に使う。
  - `合目` ・ `北麓` ・ `登山口` ・ 施設語・ルート名などのエントリは登山口側のクロスチェック用で、山頂の指数・気温には使わない。
  - 対象の山に `山頂` エントリが無く施設・登山口エントリしか無いときは、最も山頂に近い 1 つ (施設語で終わらない山名そのものの項目) を採り、山頂の値は推定である旨を強めに添える。
- 登山カテゴリ (`type=15`) は `find-mountain` のキャッシュ生成に固定してある。観光・桜など別カテゴリの地点は混ざらない。
- 県境・独立峰の山はてんくらのエントリが登山口と別の県・別の `ba` に入ることがある (例: 富士山は `ba=kk` ・コード先頭 19 = 山梨だが登山口は静岡)。コードが分かれば `ba` に依存しない。理由: `ba` は省略でき `code` + `type=15` で直に引ける。
- リスト (kasel) の CDN キャッシュによる別地域の混入は、`find-mountain --update` がエントリの `ba` echo 照合で機械的に弾く。手で `kasel.html` を取得して照合する必要はない。

### 登山指数を取得する

山のコードが決まったら `fetch-index` で取得する。`ba` は不要で `code` と `type=15` (既定) だけでよい。

```sh
# --code は前節 find-mountain で引いた対象の山のコード (下の 01150271 は別の山 = 青山の例。必ず引き直す)
deno task -q --cwd "<scripts の絶対パス>" fetch-index --code=01150271
```

スクリプトは取得・Shift_JIS デコード・キャッシュ照合・検証・抽出を一括で行い、今日・明日 (時間帯別) と週間の登山指数・気温・風を JSON で出力する。内部動作 (デコード・キャッシュ回避の突き合わせ・検証) は scripts/README.md。

出力例 (取得日 2026-08-10 (JST)。上のコマンドを実際に実行して得た実物。`tables[]` は複数あるが、構造が読み取れる先頭 1 テーブル分に絞り `fingerprint` は省略した)。

```jsonc
{
  "code": "01150271",
  "title": "青山の天気 | てんきとくらす [天気と生活情報]",
  "note": "2 回取得が一致", // どの版を採用したか
  // "fingerprint" は省略 (キャッシュ照合用の内部値)
  "tables": [
    {
      "kind": "timeband", // 時刻列 = timeband / 日付列 = weekly
      "heading": "今日8/10(月)",
      "columns": ["00", "03", "06", "09", "12", "15", "18", "21"],
      "index": [null, null, null, null, null, "A", "A", "A"], // 過去時間帯は null
      "levels": [
        {
          "alt": "高度760m付近",
          "hPa": 925,
          "temp": [null, null, null, null, null, 16, 17, 17],
          "wind": [
            { "dir": null, "ms": null }
            // ... (過去時間帯は dir/ms とも null)
            // 15/18/21 時は { "dir": "N", "ms": 4 } 等の直近時間帯の予報値 (実況ではない)
          ]
        }
        // 950hPa の level, 明日 (timeband) / 週間予報 (weekly) の table は省略
      ]
    }
  ]
}
```

出力の `tables[]` は tit_day 見出し 1 つ = 1 テーブル。`kind` は今日・明日の時刻列を表す `timeband`、または週間の日付列を表す `weekly` のいずれか。各テーブルは次を持つ。

- `columns`: 時刻を表す `00`,`03`,... または日付を表す `7/5(日)`,... のいずれか。
- `index`: 各列の登山指数 A/B/C (`mnt1/2/3.gif`→`A/B/C`。A が登山に適、C が不適)。指数と時刻・日付は同じ列インデックスで対応する。
  - `null` は過去時間帯 (表示なし) か予報範囲外の週間最先の列を指す。補完しない。理由: 欠測ではない。
- `levels`: 気圧面 `hPa` ごとの気温 `temp` と風 `wind` を持つ。単位は `temp` が℃、`wind` の `dir` が 16 方位、`ms` が m/s。過去・範囲外は null。

出力を読むときの判断 (呼び出し側の責務)。

- 山頂相当の気温は気圧面選択で決める (風は次項の別規則に従う。気温と同じ扱いにしない)。Open-Meteo の標高指定値が正常に取れているときは、この気圧面計算はクロスチェック用の比較値として算出する。どちらの値を採用するかは「4.」の選択手順 (時刻ごとに危険側を採る) に従う。
  - 表示される気圧面は日・標高で変わる (`levels[].hPa` を都度読む。ハードコードしない)。
  - 高度の目安は 950hPa が約 500m、925hPa が約 760m、850hPa が約 1500m、800hPa が約 2000m、700hPa が約 3000m、600hPa が約 4400m。この早見表は概算のフォールバックにすぎない。
  - 各気圧面の高度は `levels[].alt` (例: `高度3100m付近`) に実値が入る。理由: 早見表は概算にすぎない。早見表と食い違えば実値が正本として実値を採る。
  - 次の 3 ケースは排他で、どれか 1 つだけが当てはまる。いずれも確証が持てなければ危険側に倒す。
    - (a) 山頂が表示中の最下面より低い → 山頂標高に最も近い気圧面の値を使う。
    - (b) 山頂が表示 2 面の間に挟まれる → その 2 面を内挿した値と、直下の面から逓減率で山頂高度まで外挿した値の両方を算出し、危険側を採る (どちらか一方に決め打ちしない)。
    - (c) 山頂が表示中の最上面よりさらに上 → 最上面を基点に「4. 山頂気温の概算」の逓減率で山頂まで再外挿する。
- MUST: 上の (a)(b)(c) でいう「危険側」の向きは固定ではない。向きの決め方は「4.」の手順 1 に従う。
  - この節を単独で読んで寒い側に丸めない。暑さを問われた場面で寒い側に丸めると、暑熱リスクを過小評価して危険側に外す。
- DANGER: 風の危険側の向きも、評価するリスクで反転する。向きの決め方は「4.」の手順 1 に従う (風は気温など他要素と反転条件が異なる点もそこにまとめてある)。
  - 暑さを問われた場面で突風値などの強い風を持ち出して「風があるので涼しい」と読ませない。強い風の値は行動判断 (飛ばされ・体温低下・撤退の判断) に使うものであって、暑熱の緩和材料には使わない。
  - 次の「強い側を採る」は、断りがなければ低体温・荒天側の評価を指す。
- DANGER: 風の「強い側を採る」は、比較する軸によって可否が逆になる。先に軸を見分ける。
  - (i) 鉛直方向 (てんくらの 2 気圧面の間) では強い側を採ってはならない。下の規則に従い内挿する。理由: 高度の違う別々の大気を比べており、強い方を採っても安全マージンにはならない。
  - (ii) ソース間 (てんくらの基準値対 Open-Meteo の 10m 風・突風) と、行動時間帯の中で最悪の時刻を選ぶ時刻間では強い方を採ることが安全側になる。理由: 同じ山頂・同じ時刻を別の方法で推定した値どうし。
- DANGER: 山頂相当の風は、2 面のうち強い側をそのまま採ってはならない。山頂標高で内挿した値を基準値とする。
  - 気温と同じ内挿の式を風速に適用する (`基準値 = 下面の風速 + (上面の風速 - 下面の風速) × (山頂標高 - 下面高度) ÷ (上面高度 - 下面高度)`)。
  - 強い側を機械的に採ると、上面が山頂から離れている山で山頂の風を過大評価する。てんくらが表示する 2 面の間隔は山によって数百 m から 1000m 超まで変わり、上面が山頂より 800m 以上高いこともある。
  - その高度の風は安全マージンではない。理由: 山頂とは別の高度の大気。
  - 過大評価は「安全側だから無害」ではなく、行動可能な日を荒天と誤判定して信頼を損ない、本当に危険な日の警告を埋没させる。
- 上面の風速が基準値より明確に強い場合は、上空ほど風が強い状態 (シアー) を示す。これは基準値を置き換える理由にはならないが、稜線・肩・独立峰の山頂など風が抜ける地形では基準値を上回りうる根拠になる。
  - この場合は基準値を主に置きつつ「上空 (高度 N m 付近) では M m/s と、より強い風が予想される」と併記する。
  - 上面の値を山頂の風として断定しない。
- 内挿した基準値は下限として扱う。基準値を上限や確定値として伝えない。
  - 稜線・岩稜・独立峰では実際の風が基準値を上回るのが通常。理由: 地形加速は気圧面の値に含まれない。
- 気圧面の気温は自由大気の値 (上空の気温) であり、麓や山頂の地表気温・地表体感とは別物。これをそのまま「地表の最高気温」として扱わない。
  - 夏の低山の熱中症など地表の暑熱・体感は、気圧面気温ではなく気象庁の麓の地表気温 (アメダス) を主に見る。山頂の寒さ・風は気圧面気温に逓減率と風の体感補正を掛けて寒い側で見る。
  - 山頂が最下気圧面の高度 +300m 以内に収まる山で暑熱を評価するときは、気圧面ケース (a)(b) のどちらに落ちても、山頂の地表気温を麓アメダスの地表気温から逓減率で概算した値を同格の候補に加える (「4. 山頂気温のソースと選択手順」の条件 4)。気圧面気温は寒さ確認の補助に留める。
  - この条件は、最寄りアメダスが遠隔参考値しか無い場合 (「2.」の遠隔地点規則) と同時成立しても優先し、遠隔・概算である旨を添える。遠隔地点規則が山頂側を気圧面気温に寄せるのは寒さ評価の話で、暑熱評価には適用しない。
- 時間粒度は部位で変わる。今日・明日 `timeband` は 3 時間ごと、週間 `weekly` は当日 9 時予想の単一値。
  - ユーザが「週間」「今週」を求めた場合は両方を統合して提示する (週間だけでは当日・翌日が欠ける)。
  - 対象日が `weekly` 部にしかない今日・明日より先のときは、てんくらの指数・気温については当日 9 時予想の単一値で日内変動が取れない旨を必ず添える。この限界はてんくらのデータに限る。
  - 気温・天気・風の日内変動そのものは Open-Meteo の 1 時間値で補える。風は突風 `wind_gusts_10m` を強い側の照合に使う。
  - 登山指数の時間変化だけはどのソースでも補えない。この書き分けを回答に反映する。
- `timeband` の複数列 (時間帯) を 1 つの代表値に縮約するときは、登山の行動想定時間帯の列を採る。
  - ユーザが時刻を指定しなかった場合の既定は `06` ・ `09` ・ `12` ・ `15` ・ `18` の 5 列とする (「日中」のような語で解釈に委ねない。この 5 列は一般的な日帰り行程が収まる範囲)。
  - ただし対象の山に夜間・早朝行動が慣行的な場合 (富士山のご来光登山など) は、既定より優先して `00` ・ `03` ・ `21` を加えた全 8 列を採る。
  - この例外は非対話環境でも既定に優先する。ユーザに確認できないことを理由に既定へ落とさない。確認できない場合は範囲を広げる側に倒す。
  - 日中だけを見て夜間の寒さを落とさない。その範囲では指数の悪い列・気温の危険側の列・風の危険側の列を選ぶ。
  - 山頂気温の内挿・外挿は同一時刻の鉛直 2 点で行う (別々の時刻の値を混ぜない)。行動時間帯の各時刻で山頂気温を出し、その中で最も危険側の時刻を代表として採る。
  - 時間帯で振れが大きいとき (例: 夕方に指数が C へ急落する) は最悪の時間帯を必ず併記し、良い時間帯だけで代表させない。
  - 推定気温は単一の点でなく、危険側を端とする幅で示す (代表値は危険側)。
- MUST: 直前の時刻の縮約でいう「危険側」も、気圧面ケースと同じく向きが反転する。向きの決め方は「4.」の手順 1 に従う。暑さを問われた場面で最寒の時刻を代表に採ると、回答が質問と無関係になる (例: 日中の暑さを聞かれて早朝の最低気温を代表に出す)。
- どのテーブルがどの日かは `heading` (`今日7/3(金)` 等) で確定する。先頭 = 今日と決め打ちしない (夜遅くは今日分が落ち先頭が明日になる)。
- 登山指数は二値ではない。指数と気温・風の数値の断定に確証が持てないときは、指数 (A/B/C) を主に使い、気温・風の数値の断定は避け、山頂気温は「4. 山頂気温の概算」の逓減率で安全側に出す。
- DANGER: 指数と日付・時刻の対応を手 grep の行近接 (`grep -A`/`-B`/`-C`) で取らない。日付行と指数行は別々の `<tr>` で、行近接は指数行の先頭列を別日と取り違える (例: `grep -A5 '7/3'` が 7/1 の指数を 7/3 の指数と誤読する)。
  - スクリプトはこれを列インデックスで対応づけている。
  - スクリプトを使わず自前で解析する場合も、必ず列位置 (日付行の N 列目と指数行の N 列目が同じ日) で取る。

### 抽出の検証

- `fetch-index` が exit 1 で停止したら値を捏造しない。停止理由 (登山指数 0 件 = `type` 誤りや HTML 構造変化、`code` 不一致 = CDN が別ページを返した、テーブル抽出 0 件) を報告し、必要なら scripts・skill を更新する。
- スクリプトは `code=` と `alt="登山指数"` で取得物を照合し、cache-bust の 2〜3 回取得で CDN の別版・古い版 (日付ヘッダ・指数 gif・気圧面の fingerprint 不一致) を弾く。それでも `title`・近隣市町村名が対象の山と合うかは最終的に人が確認する。別の山・別県のデータを山頂判断に使うのは危険。
- 指数と日付・時刻の対応がずれると別の日の指数を読む。`heading` と `columns` の並びが妥当か確認し、ずれを疑ったらユーザに提示して確認する。
- HTML 構造が変わって抽出に失敗したら `scripts/cli/parse.ts` とこの skill を更新する。

## 2. 気象庁の麓の天気 (補完・クロスチェック)

てんくらの指数に加え、麓・登山口周辺の実データ (天気・気温・降水確率) を気象庁から取る。気象庁の予報は気象台 (都道府県) 単位で、その中の細分区は北部・南部・山沿いなどに分かれる。

DANGER (実行): `forecast` の取得から照合・値の抽出までを 1 つの Bash 呼び出しにまとめる。取得と抽出を別の Bash 呼び出しに分けると一時ファイルを見失って取り直しになる。理由: エージェントのシェルはコール間で cwd・変数・`mktemp -d` のパスを失う。実行時は `mktemp -d` で作った 1 つのディレクトリを使い、forecast 取得・照合・抽出を同一コマンド内で連結する。細分区・office の解決はネットワーク不要の `find-area` (次節) で先に済ませてよい。

### 区域コードを引く (find-area)

どの細分区かは地理勘で決めず、登山口の市町村名から決定的に引く。`find-area` が skill 内のキャッシュ (`assets/jma-area.json`。気象庁 `area.json` から生成済み) を使う。市町村・地区レベルの `class20s` → `class15s` → 細分区の `class10` → 気象台の office という parent 連鎖を辿る。ネットワーク不要。

```sh
# 登山口の市町村・地区名 (例: 富士宮市、松本市乗鞍上高地) から細分区と気象台を引く
deno task -q --cwd "<scripts の絶対パス>" find-area --municipality=富士宮市
# => {"matches": [{"class20": {"name": "富士宮市", ...}, "class10": {"code": "220030", "name": "東部"}, "office": {"code": "220000", "name": "静岡県"}}]}
```

- 0 件のときは exit 1 で止まる。より広い市名・近隣地名で引き直し、市町村合併等でキャッシュが古い可能性があれば `--update` で取り直す。

- 細分区名は都道府県ごとに異なる (北部・南部、内陸・沿岸、南部山沿い・北部平野部など)。固定の名前を決め打ちせず、必ず上の方法で登山口の市町村から細分区を引く。
- `class20s` の地区名は細かい (例: `松本市乗鞍上高地`)。登山口に対応する地区語で引くと精度が上がる。市町村名でヒットしないときは、より広い市名や近隣地名で引き直す。
- てんくらが表示する「近隣市町村」は山頂位置基準で選ばれ、登山口と一致しないことがある。気象庁の細分区・アメダスは必ず登山口の実所在地から独立に引き、ソース間で地点が違えば回答に明記する。
- 登山口が複数県にまたがる山 (例: 富士山の吉田口 = 山梨と富士宮口 = 静岡) でルートが未指定の場合は、主要登山口を複数併記するか、ユーザにルートを確認する。1 つの登山口に決め打ちしない。
- 山沿い・内陸の区分がある県では、山に近い区を優先する。平野部の天気は山と乖離しやすい。
- 北海道は登山口を管轄する office を選ぶ。理由: 気象台が複数に分かれる。

### 予報を取得する (forecast)

```sh
# mktemp -d で実行ごとに一意なディレクトリを作る (固定パスは並行タスクと衝突する。「注意」参照)
# 例は前節の find-area (富士宮市) に合わせ、静岡県 (office=220000) で統一する
tmpdir=$(mktemp -d)
curl -sS 'https://www.jma.go.jp/bosai/forecast/data/forecast/220000.json' -o "$tmpdir/forecast.json"
```

配列は 2 要素で `[0]` が 3 日予報、`[1]` が週間予報。`[0].timeSeries` は 3 本あり区分単位が異なる。

| timeSeries | 内容                                                     | 区分単位                    |
| ---------- | -------------------------------------------------------- | --------------------------- |
| `[0]`      | 天気 `weathers` ・天気コード `weatherCodes` ・風 `winds` | 細分区 (class10)            |
| `[1]`      | 降水確率 `pops`                                          | 細分区 (class10)            |
| `[2]`      | 気温 `temps` (最低・最高)                                | アメダス観測地点 (麓の地点) |

天気・降水確率は細分区単位だが、気温だけはアメダス地点単位で粒度が違う。気温を細分区から探すと空振りする。3 日予報の temps は timeDefines の 00 時が最低・09 時が最高に対応するのが通例だが、位置に意味を決め打ちせず、週間予報側の tempsMin/tempsMax と突き合わせて解釈を確認する。

```sh
# 天気・風 (細分区コードで絞る。富士宮市が属する東部 220030)
jq '.[0].timeSeries[0].areas[] | select(.area.code == "220030") | {area: .area.name, weathers, winds}' "$tmpdir/forecast.json"
# 降水確率
jq '.[0].timeSeries[1].areas[] | select(.area.code == "220030") | {area: .area.name, pops}' "$tmpdir/forecast.json"
# 気温 (アメダス地点。登山口に最も近い地点を名前で選ぶ)
jq '.[0].timeSeries[2].areas[] | {name: .area.name, temps}' "$tmpdir/forecast.json"
```

出力例 (取得日 2026-08-10 (JST)。直前の curl + jq 3 コマンドを実際に実行して得た実物。数値・予報文はその時点のもの)。

```jsonc
// 天気・風
{
  "area": "東部",
  "weathers": [
    "晴れ　後　くもり　夜遅く　雨　所により　昼過ぎ　から　雷を伴い　激しく　降る",
    "くもり　朝晩　雨　所により　雷　を伴う",
    "くもり　時々　雨"
  ],
  "winds": ["東の風", "東の風　日中　西の風", "東の風"]
}
// 降水確率
{ "area": "東部", "pops": ["30", "50", "50", "30", "30", "50"] }
// 気温 (アメダス地点。富士宮口の登山口に近いのは三島。他地点は省略)
{ "name": "三島", "temps": ["33", "33", "25", "29"] }
```

- 気温のアメダス地点は登山口に最も近いものを名前で選ぶ。判断できない場合は複数地点を併記して幅で伝える。憶測で 1 地点に決め打ちしない。
  - 最寄り地点が登山口から離れているときは、その 1 点を「遠隔地点の参考値」と明記して採り、山頂側の気温は Open-Meteo の標高指定値 (取れなければてんくらの気圧面気温) を主とする。序列は「4.」に従う。
  - 離れている例は 3 つある。
    - 県に近傍地点が 1 つも無い場合。例: 東京は都心・離島のみ。
    - 最寄りは在るが水平距離が遠い場合。例: 富士宮口に対する三島。
    - 最寄りでも登山口と標高差が大きい場合。例: 標高約 1100m の旭岳の登山口と、標高約 120m の平地にあるアメダス旭川。
  - 近い・遠いの線引きは、目安として登山口から水平 20km 超、または標高差 500m 超のいずれかに当たれば遠隔参考値として扱う。どちらも下回るなら近傍地点として扱ってよい。
  - この目安で決まらないときは遠隔参考値の側に倒し、断定を避ける。閾値の近傍 (水平 15〜20km、標高差 400〜500m 程度) に来たときも遠隔側に倒す。
  - 判定に使う登山口の座標・標高には、山頂のような確定手段を課さない。理由: 取得元が無い。
  - 登山口の位置が確定できない場合は計算を省き、遠隔参考値の側に倒す。手元の概算値で判定して近傍と断定しない。
  - 遠隔参考値を暑熱評価に使うときは、登山口側がこれより暑い可能性 (都心・沿岸の地点と内陸の登山口の傾向差) を注記する。
- 各値がどの日時に対応するかは同じ `timeSeries` の `timeDefines` で必ず確認する。配列の index に意味を決め打ちしない (取得時刻によって入る要素が変わる)。
  - `[0]` 内でも系列ごとに終端日が揃わない (深夜取得では weathers に翌日があっても pops/temps が当日までのことがある)。
  - 目的日の値が timeDefines に無ければ週間予報 `[1]` へフォールバックし、県単位・遠隔地点の参考値である旨を必ず併記する。
  - 初回の同一コマンド内で 3 日予報 `[0]` の weathers・weatherCodes・winds・pops・temps と、週間予報 `[1]` の weatherCodes・pops・temps を無条件に抽出しておく。理由: フォールバック要否は抽出後にしか分からない。後から要ると分かって取り直さない。
  - `[0]` の weathers・weatherCodes は必ず初回リストに含める。理由: 後述の天気コード和名照合にも使う。
- 取得した forecast が別の県の内容になっていないか検証する。レスポンスの `publishingOffice` と `areas[].code` の先頭桁が要求した office と一致するか確認し、不一致なら (キャッシュ等で別府県を掴んでいる) 取り直す。
  - 別県の予報を山頂判断に使うと危険。
  - 取り直すときはクエリ文字列 (例: `?_=1`) を付けるか `-H 'Cache-Control: no-cache'` で CDN キャッシュを回避する。
- 数日先 (週間予報 `[1]`) は粒度が落ちる。weather・降水確率が細分区ではなく office (県) 単位、気温がアメダス少数地点になり、登山口近傍の細分区・地点が得られないことがある。
  - 時間粒度も落ち、降水確率・天気は日単位の代表値になる (時間帯別は取れない)。その場合は県単位・遠い地点・日単位の値だと明記して参考扱いにする (地点粒度と時間粒度の両方の低下を併記する)。
  - 最寄りアメダスの目的日の値が取れないときは、同地点の当日・直近日の値を「別日の参考」とラベルして添えてよい (目的日の値の代用にはしない)。
  - 3 日予報と週間予報の両方に同一日・同一対象の値があって食い違う場合も、ソース間の食い違いと同じ原則 (危険側を採り両方併記) で扱う。
- `publishingOffice`・`area.code` が正しい県でも、気温 `timeSeries[2]` のアメダスだけ別県が混入することがある。理由: office・code 照合では気温の県跨ぎを検出できない。
  - 気温地点名が対象県の地点か照合し、県外の地名が出たらキャッシュを回避して取り直す。別県の気温で山頂を概算するのは危険。
- 天気コードの和名は別ファイルに頼らず、同じ forecast の `[0].timeSeries[0].weathers` (日本語文字列) で同コードの意味を確認する。週間部だけに出るコードが `[0]` に無いときは、コードの百の位が 2xx = くもり系・3xx = 雨系・4xx = 雪系のいずれかで安全側 (降水・降雪あり前提) に解し、ピンポイントの和名は断定しない。
- 発雷は山で最も危険な現象の 1 つ。理由: 小屋以外に逃げ場がない。
  - `weathers`/`weatherCodes` に雷 (「雷」の語・コードの一部) が出たら、時間帯と併せて必ず強調する。ピンポイントの天気マークに出ていなくても、周辺の細分区・広域の概況に雷傾向があれば急変の兆候として扱う。
- 登山前日の天気も確認する。前日が大雨だと登山道のぬかるみ・沢の増水・土砂崩れが当日の行動に影響する。当日分の予報だけで判断せず、前日の降水を併せて見る (前日に予報を取得しておく、または当日にアメダスの前日降水量で補う)。

## 3. Open-Meteo の山頂数値予報 (標高指定の第三のソース)

山頂の緯度・経度・標高を指定した数値予報を Open-Meteo (`api.open-meteo.com`) から取る。キー不要・非商用無料の JSON API で、`elevation` に山頂標高を渡すと 90m DEM ベースの標高補正が適用された値が返る。取得・検証は `scripts` の `fetch-openmeteo` に集約してある (内部動作は scripts/README.md)。

```sh
# 例は富士山頂 (3776m。剣ヶ峰の公称標高。アメダス富士山地点の3775mとは別。「前提」の例外節参照)
deno task -q --cwd "<scripts の絶対パス>" fetch-openmeteo --lat=35.3606 --lon=138.7274 --elevation=3776
```

出力例 (取得日 2026-08-10 (JST)。上のコマンドを実際に実行して得た実物。`hourly[]` は `--days` × 24 レコード続くが、構造が読み取れる先頭 1 レコード分に絞った)。

```jsonc
{
  "source": "Open-Meteo (https://open-meteo.com/)",
  "license": "CC BY 4.0",
  "latitude": 35.35, // モデル格子に丸めた値が返る
  "longitude": 138.75,
  "elevation": 3776, // 指定値と一致することを検証済み
  "timezone": "Asia/Tokyo",
  "units": {
    "temperature_2m": "°C",
    "relative_humidity_2m": "%",
    "wind_speed_10m": "m/s",
    "wind_gusts_10m": "m/s",
    "precipitation": "mm",
    "precipitation_probability": "%",
    "freezing_level_height": "m",
    "weather_code": "wmo code"
  },
  "hourly": [
    {
      "time": "2026-08-10T00:00",
      "temperature_2m": 1.7,
      "relative_humidity_2m": 95,
      "wind_speed_10m": 3.24,
      "wind_gusts_10m": 5.9,
      "precipitation": 0,
      "precipitation_probability": 41,
      "freezing_level_height": 4930,
      "weather_code": 2
    }
    // 以降 1 時間ごと × --days 日分 ...
  ]
}
```

- 引数は `--lat` ・ `--lon` ・ `--elevation` (いずれも必須で、標高は山頂の m)。
  - `--days` は任意 (既定 3、最大 7)。
  - timezone は Asia/Tokyo、風速単位は m/s に固定してある。
- 出力は 1 時間ごとのレコード `hourly[]` で、気温・湿度・風速・突風・降水量・降水確率・凍結高度 (`freezing_level_height`)・天気コードを持つ。単位は `units` に入る。
- スクリプトはレスポンスの `elevation` が指定値と一致することを検証する。不一致・HTTP エラー・`error: true` のレスポンスは exit 1 で停止する。停止したら値を捏造せず理由を報告する (取得失敗時は止めて報告する原則)。
- 山頂の緯度・経度・標高は、検証を通した値だけを渡す。ここでの「憶測で置かない」は最終的に渡す座標に掛かる制約であって、検証前の候補を出すことは禁じない。
  - 候補は手元の知識・地図から出してよい。必須なのは、その候補を必ず次の標高検証に通し、通らなければ次項の手順で修正すること。検証を通さずに候補をそのまま渡すことだけを禁止する。
  - 確定手段: 国土地理院の標高 API (`https://cyberjapandata2.gsi.go.jp/general/dem/scripts/getelevation.php?outtype=JSON&lon=<経度>&lat=<緯度>`) に候補座標を渡し、返る標高が対象の山頂標高と数十 m 以内で一致することを確認してから使う。大きくずれる座標は山頂を指していない。
  - レスポンスの `latitude`/`longitude` はモデル格子に丸めた値が返るが、`elevation` は指定値がそのまま echo される (これを検証に使う)。
- 検証で外れた場合は、座標を憶測で置き換えず次の手順で山頂を特定する。外れたまま進めると、隣接する別の山の予報を対象の山として報告することになる。
  1. 候補座標の周辺を格子状にサンプリングし、標高の最大点を探す。国土地理院の標高 API を格子の各点に対して引き、最も高い点を候補にする。刻みは 0.001 度 (約 100m) 程度から始め、範囲は候補座標の周囲 0.005〜0.02 度を目安にする。
  2. MUST: 最大点が探索範囲の端に来た場合、その値を採用しない。範囲外にさらに高い地形が続いていることを意味し、多くは隣の別の山の斜面を拾っている。中心をずらすか範囲を広げて引き直す。
  3. 端に張り付く状態が続く場合は、最大点を求めるのをやめ、候補座標から周囲 8 方向のうち最も標高が高い点へ移動する操作を、改善が止まるまで繰り返す (山を登る形で局所的な頂点に到達する)。これで隣の高い山へ吸い寄せられずに、対象の山自身の頂点が得られる。
  4. 得られた点の標高が公称の山頂標高と数十 m 以内で一致することを確認する。一致しなければユーザに確認する。理由: 対象の山ではない。
- 岩峰・岩塔の山頂は、標高 API の値が公称標高より低く出ることがある。理由: 標高データは一定間隔の格子の代表値で、鋭い岩峰は平滑化されて削られる。
  - 判定の閾値は次のとおり。公称より低い側は 80m 以内の不足なら許容し、正しい山頂として採用する。
  - 80m を超えて不足する場合は次項の探索手順へ回す。理由: 座標が山頂を外している疑いが強い。
  - 逆に公称標高より 100m 以上高く出る場合は別の山を指している可能性が高い。
  - 許容範囲内の不足で正しい山頂を捨てない。理由: 低く出ること自体は座標の誤りを意味しない。
- Open-Meteo に渡す `--elevation` は公称の山頂標高を使う。標高 API の実測値ではない。理由: 上記のとおり岩峰では低く出る。
- `weather_code` は WMO コードの数値のまま出る (スクリプト側で和名変換しない)。大まかな系列 (0〜3 = 晴れ〜くもり、45/48 = 霧、5x = 霧雨、6x = 雨、7x = 雪、8x = にわか、95 以上 = 雷雨) で安全側に読み、細かい和名の断定はしない。95 以上 (雷) が出たら時間帯と併せて必ず強調する。
- `freezing_level_height` (凍結高度) が山頂標高を下回る時間帯は山頂付近が氷点下になりうる。防寒・凍結・降雪のリスクとして必ず伝える。
  - 逆に凍結高度が山頂より上でも、直接値の `temperature_2m` が氷点下ならそちらを採って氷点下として扱う。直接値と派生指標が食い違うときは常に寒い・危険側を採る。
  - 降水の相 (雨か雪か) は `weather_code` を正とし、凍結高度は補助に留める。両者が矛盾するとき (例: 凍結高度が山頂より上なのに雪コードが出る) は危険側の雪・凍結側で伝える。
- 降水量・降水確率・`weather_code` が食い違うとき (量 0 なのに確率が高い等) も危険側で読む。確率が高ければ量 0 でも「降りうる」前提で伝え、雨具・行動打ち切りの判断材料に含める。
- 風の取得元の主体と食い違ったときの採り方は「4.」の風の規則に従う。Open-Meteo の `wind_speed_10m` は地形加速が載らず過小になりうるため参考値に留め (「限界をユーザに伝える」参照)、`wind_gusts_10m` は強い側の照合に使う。

## 4. 山頂気温の概算 (Open-Meteo 主・標高差フォールバック)

山頂気温には取得元が 3 つある。どれを回答の数値に採るかは、次の手順で一意に決める。ソースごとに固定の序列を持たせるのではなく、時刻ごとに危険側の値を採る。

### 山頂気温のソースと選択手順

| ソース                    | 中身                                       | 位置づけ                           |
| ------------------------- | ------------------------------------------ | ---------------------------------- |
| Open-Meteo の標高指定値   | 山頂標高で補正した 1 時間ごとの数値予報    | 基準ソース (既定の出発点)          |
| てんくらの気圧面気温      | 自由大気の値を山頂標高で内挿・外挿したもの | 同格の比較対象                     |
| 麓アメダス + 逓減率の概算 | 麓の地表気温から標高差で外挿したもの       | 暑熱評価では同格、寒さ評価では補助 |

手順は次のとおり。

1. 危険側の向きを決める (この skill 全体の権威ある定義。他の節はここを参照する)。低体温・荒天の評価では寒い側が危険側。夏の暑熱・熱中症の評価では暑い側が危険側。
   - 同じ回答の中で両方を扱うなら、項目ごとに向きを分けて別々に算出する (一方の向きで出した値を他方へ流用しない)。
   - 両方向を出したときの提示は、1 つの気温値に丸めず、リスクごとに分けて併記する。書き方は「寒さ (低体温) 側: 山頂 X ℃ (時刻・条件)」「暑熱側: 山頂 Y ℃ (時刻・条件)」の 2 項目とし、どちらが主でどちらが従かを付けない。
   - 両者は別のリスクの評価であって同じ量の上下限ではないので、レンジ (X 〜 Y ℃) の形にまとめない。
   - **風だけ向きが反転する**: 低体温・強風・荒天の評価では強い風が危険側だが、暑熱・熱中症の評価では弱い風が危険側 (風が弱いと汗が蒸発せず放熱できない)。気温・指数・気圧面選択などの他要素の向き (暑い側 = 危険) をそのまま風に流用しない。
2. 各ソースの代表値を先に 1 つへ畳んでから、同一時刻で並べて危険側を採用値とする。畳む順序を先に固定しないと、ソース内の選択肢 (てんくらの内挿値と外挿値) とソース間比較が入れ子になり、結果が実行ごとに変わる。
   - てんくらの代表値は「1.」の気圧面ケース (a)(b)(c) で算出した値のうち危険側の 1 つとする (寒さ評価なら内挿と外挿の寒い方、暑熱評価なら暑い方)。
   - 比較は必ず同一時刻の値同士で行う (てんくら週間部の 9 時単一値と比べるなら Open-Meteo も同日 9 時の値を使う)。
3. MUST: 採用ソースは時刻ごとに入れ替わってよい。「このソースを主にする」とソース単位で固定しない。
   - 実際に早朝は Open-Meteo が寒く、日中は気圧面が寒い、というように逆転する。ソース単位で主従を決めると、逆転した時刻で危険側を取り落とす。
4. **麓アメダス + 逓減率の概算を同格に上げる条件**: 山頂が最下気圧面の高度 +300m 以内に収まる山で、暑熱を評価するとき。この条件は標高だけで判定でき、リスクの種類を判定基準に含めない。
   - 条件に当てはまるとき、地表の暑さの評価には気圧面気温を使わず、寒さ確認の補助に留める。理由: 気圧面気温は自由大気の値。

### 省力化と、その打ち切り条件

全時刻でソース比較するのが基本だが、行動時間帯内の代表 2 時刻以上でのクロスチェックに省略してよい。

- MUST: 省略する場合、代表時刻の間でソースの優劣が逆転していたら省略をやめ、行動時間帯の全時刻に展開して評価し直す。サンプルの外で危険側が入れ替わっている。理由: 逆転はソース間の系統差ではなく時間変化を意味する。
- MUST: 代表時刻は 1 点にしない。1 点では逆転を検出できず、省力化が安全側の原則を壊す。
- MUST: 代表時刻には行動時間帯の両端 (最初と最後の列) を必ず含める。サンプル数だけ満たしても位置が中央に寄っていると逆転を検出できない。実際、早朝と日中でソースが入れ替わる事例があり、中央 2 点 (例: 9 時と 15 時) を選ぶと早朝の最も危険な値を取り落とす。
- てんくら週間部のように、そのソースが 1 日 1 個の値しか持たない場合は、ソース間比較が単一時刻でしか成立しない。このときは省略の話とは切り離し、「幅の作り方」の単一時刻比較の扱いに従う (比較できた時刻を明記し、他時刻も同程度ずれうる旨を幅の悪い側へ注記する)。理由: 上の MUST を満たせない。

### 幅の作り方

- 提示する幅は採用側の不確実性 (時間帯の振れ・逓減率の幅) で構成する。ソース間の乖離を幅に混ぜて広げない。乖離が大きいときは危険側ソースの値を代表・幅とし、他ソースの値は「別ソースでは X ℃」と注記で併記する。
- 「乖離が大きい」かの判定は標準逓減率 (0.6) での推定値と採用値の差で測る。迷ったら閾値の議論で止まらず危険側を代表にする。
- 単一時刻でしか比較できない場合、その時刻の乖離を他時刻へ定数として展開しない。乖離の事実は「他の時刻も同程度ずれる可能性がある」という幅の悪い側の注記としてのみ反映し、代表に採った時刻が比較できた時刻と異なるときはその旨 (比較は 9 時のみ等) を添える。
- Open-Meteo の値は数値予報の生値であり山頂の実測ではない (「限界をユーザに伝える」参照)。行動時間帯の既定と安全側の列の選び方は「1.」の timeband 縮約規則と共通で、Open-Meteo の 1 時間値の縮約にも同じ規則を適用する。

Open-Meteo が取得できない場合 (API 停止・ネットワーク断・`fetch-openmeteo` が検証不一致で停止した場合) は、次の標高差からの概算にフォールバックする。てんくらが上空の気温を出すが、取れない場合や麓のデータしかない場合も同様に標高差から概算する。いずれも推定であり山頂の実測ではない。危険側に倒し、下振れに丸めない。なお、てんくらの上空気温は参照気圧面の値 (例: 800hPa は約 2000m) で、山頂標高より低いことがある。その場合はてんくら上空気温を基点に、下式で山頂標高まで再外挿する。

標高が 100 m 上がるごとに気温は約 0.6 度下がる (気温逓減率)。

```text
山頂気温の概算 = 麓の気温 - 0.6 × ((山頂標高 - 基点標高) / 100)
```

- 基点標高は「その気温を観測・予想した地点の標高」を使う。アメダス地点の値ならアメダス地点の標高、登山口の値なら登山口標高。
  - 遠隔アメダスの気温を採ったのに基点だけ登山口標高にすると差し引きがずれる。
  - アメダス地点の標高は気象庁の地点一覧 (`https://www.jma.go.jp/bosai/amedas/const/amedastable.json`、地点名 `kjName`・標高 `alt`) で引ける。
  - 引けないときは 0m とみなしてよいが、その簡略化と向き (山頂側の概算が涼しく出る) を回答に明記する。
- 式の入力 (基点標高・山頂標高) は地図・公的資料から確定し、概算値を使ったときはその旨を回答に明記する。取得手段の無い変数を勝手な精度で断定しない。
- 逓減率 0.6 度/100m は標準的な目安。晴れて乾いた日は約 1.0、湿って雲が多い日は約 0.5 と幅がある。
  - 選ぶ順序は、まず当日の天気から決め、決まらない分だけを危険側に倒す。天気コード・雲量・降水の有無が取れているなら、晴天・乾燥なら 1.0 寄り、曇天・降水ありなら 0.5 寄りを採る。
  - 天気が読めないときに限り危険側の値を採る。この順序を飛ばして常に危険側の端 (寒さ評価なら 1.0) を機械的に使わない。
  - 気圧面の 2 面から求まる実効逓減率が 1.0 を下回る日にそれを続けると、外挿値が常に内挿値より寒く出て「両方算出して危険側を採る」が「常に外挿」に退化し、山頂気温を実態より寒く報告し続けることになる。
  - 過大な寒さの見積もりは、風の過大評価と同じく本当に危険な日の警告を埋没させる。
  - 向きの決め方は「4.」の手順 1 に従う (低体温・荒天の評価では大きい側 (1.0 寄り) が、暑熱・熱中症の評価では小さい側 (0.5 寄り) がここでの危険側になる)。「迷ったら大きい逓減率」と固定しない。
- 体感温度は風速 1 m/s ごとに約 1 度下がる。麓基準より厳しくなる前提で伝える。理由: 稜線・山頂は麓より強く吹くのが通常。
  - 風速は「1.」の風の規則で採る (2 気圧面を山頂標高で内挿した基準値を使い、強い側をそのまま採らない)。風の取得元の主はてんくらの気圧面風とし、Open-Meteo の 10m 風・突風と食い違うときは体感補正に強い側を採る。
  - 風も気温と同じ 2 段階で処理する: まず同一時刻の値同士でソース間比較して強い側を採り、次に行動時間帯の中の最悪 (最強) の時刻を代表に選ぶ。
  - この 2 段階はいずれもソース間・時刻間の比較であり、てんくらの 2 気圧面の間で強い側を採ることではない。
- 最低気温側で氷点下・一桁になるなら、防寒・低体温のリスクとして必ず伝える。

## 注意

- 取得結果には対象の山・都道府県・細分区・アメダス地点・日時を必ず添える。どの地点・どの時間の値かを曖昧にしない。
- 「ユーザに確認する」と指示された分岐 (同名の山・登山口ルート・行動時間帯など) で確認が取れない実行環境では、止めずに仮確定して進める。採った仮定と識別キー (`code`・`pref` 等) を回答に必ず明記する。
  - 仮確定の基準は分岐の性質で分かれる。
  - どれか 1 つが正解である同定の分岐 (どの山か・どのルートか) は、地名・`pref`・標高・慣行といった依頼文の文脈から最も蓋然性の高い候補を採る。理由: 別の山を選べば単に誤りであり、ここに安全側という方向は無い。
  - 値の幅を選ぶ分岐 (行動時間帯・逓減率など) は危険側に倒す。
  - 複数の解釈が同程度に成り立つ場合は全候補を併記する。
- この skill が扱うのは天気の判断のみ。開山期・登山道の開通/通行止め・入山規制・登山届などは天気とは別事項で、skill 側で開通可否を断定しない。該当しそうな場面 (例: 富士山の週末が開山前) では「天気とは別に開通状況を必ず確認する」と一言添えるに留める。
- 登山指数は同社の独自指標、山頂気温・体感温度は推定であり、いずれも山頂の実況を保証しない。断定せず、安全側に倒して伝える。
- てんくら・気象庁のデータは明示的なオープンデータライセンスが確認できていない。取得した生データの無断の二次配布・公開はしない。Open-Meteo のデータは CC BY 4.0 で、ユーザへの提示時に出典 (Open-Meteo) を添える。
- scripts の実行は必ず `deno task -q` で行う。`-q` が無いとタスクランナーのバナー行が stdout に混ざり、`jq` 等での機械処理が壊れる。
- 気象庁側で使う一時ファイル (`forecast.json`) は `mktemp -d` で実行ごとに一意なディレクトリを作りその中へ置く。理由: 固定パスは並行タスクに上書きされ、別対象のデータを掴む事故が起きる。
  - 後続の `jq` も同じ絶対パスを参照し、照合と値の抽出は同一コマンド内で行う。
  - 山コード検索 `find-mountain`・区域解決 `find-area`・てんくら取得 `fetch-index`・Open-Meteo 取得 `fetch-openmeteo` は一時ファイルを手で持たない。理由: script が一括で行う。
- 取得・抽出に失敗した場合 (`find-mountain`・`find-area` が `--update` しても 0 件/`fetch-index` が登山指数 0 件で停止/`fetch-openmeteo` が elevation 不一致で停止/forecast の構造が変わる等) は値を捏造しない。処理を止めて報告し、scripts・skill を更新する。
